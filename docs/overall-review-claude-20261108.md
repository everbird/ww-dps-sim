## 0. 已对齐的方向

1. **底座优先。** 首要目标是可靠、可复用的逐帧仿真底座。教学轴是第一个要跑通的场景。锚定视频轴（录像剖析）以后再支持，它和深塔、矩阵一样，是用来检验底座的应用。
2. **教学轴是确定的。**
   - 假设明确为"一能按就按"；
   - 不用补位 `~`、可选 `?`，动作都是确定的；
   - 要取消就在轴里写明取消哪个动作、什么时机；
   - 谐度破坏按轴写明的时机放，不自动放。

   教学轴里出现不确定的因素，说明轴写得不对，应改轴，不是接受它。"一能按就按"在现有规格里的精确含义，以及还要定的几处，见 §1.5。

   这里的"确定"指动作由作者写明，不让调度器替作者选动作。引擎本身对任何输入都是确定的（第 3 条）；`~`、`?`、自动谐破也是确定的策略，排除它们是教学轴的操作约定（第四版补，采纳 Codex `codex-debate.md` CD-01）。
3. **引擎自洽、确定。** 给定数据、规则、配置与轴，逐帧结果唯一。底座不要求一开始就 100% 贴合游戏。贴不贴合是"用哪些数、用哪条规则"的问题，靠之后的收敛解决。
4. **剩下的变化只来自规则与数据。** 同一条轴的结果会变，只能是因为规则或数据换了。没证实的规则都做成能翻的开关。
5. **规则是动态收敛的。** 现有数据源没提供规则，要自己摸出来。做得够好时，规则应能收敛到基本贴合游戏。一条规则依次经过发现、登记为待验证、翻开关比较、针对性实验，最后证实或否定。游戏版本更新后可能重新打开。
6. **结果说明自己用了哪些规则。** 像配置或环境变量一样让调用者知道，包括全部开关的快照，以及实际影响了这次结果的那几条。
7. **追溯链路不丢。** 底座要能被 AI agent 直接拿来做分析，从结果追到原因的链路不能丢东西。
8. **外力和核心隔开。** 锚定视频轴的外力写法（钉时刻、直接改状态）和核心隔开，结果里标明哪些状态是外部指定的、不是规则推出来的。

## 1. 讨论中的更正

### 1.1 "时刻编译时定不下来"：收回

我最初说引擎"更像模拟器而不是编译器"，理由之一是"时刻编译时定不下来"。当时举的例子：中 3 第三轮 107.4 秒，仿真能量 119/125，引擎等能量，后面一次切人晚了 1.9 秒（`tower-20261026.md` 中 3）。

用户指出：教学轴在理想情况下、符合所有规则时，动作按顺序排下来，每一帧怎样是确定的。

结论：这句用词不对，收回。
- 我想说的只是"时刻要逐帧算出来，读轴写不出来"。就像棋谱：着法定了，终局就定了，但要照着摆一遍才知道。这不是不确定。
- 中 3 的例子属于锚定视频轴，不属于教学轴。
- 逐帧事件流是运行的结果（运行记录）。这只是叫法上的区分，不影响方向。

我还举过"一能按就按不一定最好"的例子（`engine-quality-plan.md` §5 P1：C8 两处晚 6 帧，一轮反而短 21 帧，+1.11%）。原因正是自动谐度破坏换了时机，所以它反倒支持 §0 第 2 条：自动的东西不该进教学轴。谐度破坏写明时机后，"晚一点更好"就成了轴作者的选择，不再是引擎里的意外。

### 1.2 "没有规范"：采用用户的说法

我原来说"鸣潮没有规范"。用户的说法更准：规则是存在的，只是目前的数据源没提供，要自己摸出来，最终应能收敛到基本贴合游戏。§3 按这个说法写。

数和规则要分开看：
- **数有来源**：xlsx、解包给的是倍率、帧数、能量值。
- **规则没有表会写**：这些数怎么相互作用，比如切人冷却全队共用还是每人各算、大招过场里自己命中的顿帧算不算时间、阵附加的异常效应算不算角色附加的。

TD-04 到 TD-07 就是自己写下的规则，是对游戏的推测。

### 1.3 应用与实验的分工：用户的理解成立，补两类

用户的理解是：应用里发现的，本质上是没有可靠信源的数据；靠实际情况校准时发现可调的选项，再设计实验证实。这个理解成立。补充：应用发现的有三类。

1. **有数，但没出处或不准**：帧数只有 xlsx 一家。适合校准加实验。
2. **有数，但不知道要用它**：声骸起手优先级。xlsx 通用块"召唤声骸 / 变身声骸"行的优先级 5 一直在，调度没拿它来比（AGENTS 差异 21）。
3. **没有数，只有规则**：切人冷却每人单独计（差异 18）、大招过场里的自身顿帧（差异 49）。

后两类在发现之前，不知道那里有一个可调的选项。查提交记录，`echo-input-priority`（3752451）、`hitstop-in-global-stop`（25b0a6f）、`switch-ends-stop`（18225fb）都是在修复的同一个提交里才第一次登记成假设。

所以分工是：
- **应用**（教学轴、录像）：发现"这里原来有个旋钮"，并指出哪些旋钮影响大；
- **实验**：把旋钮拧到正确的位置，即证实；
- **调参**：只在已知旋钮的合理范围里找值，主要用于第 1 类。

我问过"录像时刻动作放不出时，要不要直接报出差异和原因"。原型已经有了：

- `insight` 汇总被挡住的时间；
- 视图 F 与 `pnpm trace` 逐个对照录像时刻。

### 1.5 教学轴的确定性：现有语义与还要说清的

这一节是通读设计与调度器代码后补的，用户没有逐条讨论过；结论性的部分列进 §10，供评审定。

**现有规格已经把"一能按就按"定得很细。** 依据是总设计 T6、T7，TD-04 §6.4，TD-09 §3.4，以及假设 `earliest-frame`（"没有反应时间，算的是理论上限"，影响"大"）。"能按"是以下三项同时满足：
- **动作层面合法**：优先级、派生窗口、连段前置、输入锁都允许；
- **状态条件满足**：冷却、资源、角色条件（钩子 `canStart`）；
- **当前动作已就绪**：这是默认要求，指现在打断不会丢判定、资源或延奏。

此外，`!` 跳过"就绪"，按游戏规则允许的最早时刻打断；`+N` 是刻意晚 N 个战斗帧。等不来就报错（T7）。

**调度器还有几处替轴选时机的等待。** 原型里除了 `~`、`?`、自动谐度破坏，还有这几种，都在 `scheduler.ts`、都是确定的，日志里各有等待代码：
1. 默认等就绪（`settled`）：例如"散华 A1 E"，E 要等 A1 第 13 帧出手。
2. 写了"变奏"的切人，切出者协奏没满时，等手上动作的判定出手再切（`settled`），因为这几下的协奏可能正好补满。
3. 切进来的第一下是空中攻击时，等切出者跳起（`airborne`）。
4. 切进来的第一下是地面出场技时，等切入者自己在后台的动作走完（`entryBusy`）。

第 1 条是 TD-04 定稿的"能按"的定义；第 2–4 条是调度器按轴写的意图（要变奏、要空中入场、要出场技）推出来的时机。要评审定的是：后三条算"一能按就按"定义的一部分、写进教学轴模式的规格，还是算"轴没写清"、要求在轴里写明（§10 第 5 条）。我倾向于前一种，但要在规格里逐条列出，结果里也标出"这次哪几处是调度器按意图选的时机"。Antigravity 也是这个意见。

**意图没达到，在严格入口里是失败**（第四版补，与 Codex CD-01 达成共识）。现在三种"按意图"的写法口径不一：
- **变奏**：写了"变奏"而协奏不够，照常普通切人，只记 `introMissed` 警告；
- **空中入场**：不成立时报错 `airEntry`；
- **出场技**：不成立时报错 `entrySkill`。

严格入口要统一成"意图未满足"：说明是哪条指令、缺什么、执行到了哪一帧；之后的结果可以继续给诊断，但不算原轴成立。普通切入不算"变奏"的成功，因为变奏动作、延奏 buff 和协奏清零都是轴的一部分。约定放在入口层（编译期查写法、运行时查意图），复用同一个执行器；`~`、`?`、自动谐破不必删，但不写进底座契约，去留由用户决定。

**等待和阻挡的原因分三类**（第三版补，采纳 Codex §3.3）：
- **所选模型下的游戏限制**：能量不够、冷却、输入锁；
- **调度策略**：等出手、按意图推出的等待；
- **外部给定的条件**：`at`、能量满、指定失谐。

结果里按类标出来，应用才分得清"游戏不允许""调度器替你选了时机""是你指定的"。`whyNot` 还要说明返回的是第一个挡住的条件还是全部条件：现在调度器多处遇到第一项就返回。

**结果的叫法要准**（第三版补）：
- **"上限"不等于最优时序**：按最早合法帧执行的结果，未必是这条轴在时序上的最优。`insight` 的卡帧点里出现"晚一点反而更好"时，要作为提示列出来，多半是某个按意图的等待或 buff 窗口错开了。
- **"必要"要附条件**（Codex §8）：说某个动作"必要"，意思是在这个起点、保留后面这些操作和目标时不能删，不等于所有打法都要它。

**取消和谐度破坏要能写进轴。**
- **原文本来就写了**：教学轴原文已经写明"闪""跳""处决"的位置。例如景尤守 5R18Z 的文字轴写的是"变奏景qr zaaa处决 eaz eaz"（`~/wuthering-waves/` 里的整理）。
- **WuwaLAB 也这样做**：它的轴把取消方式（普通、闪避、无敌取消）与取消帧、切人帧当作轴本身的一部分，由作者填写（`rotation-video.md` §2）。10-22 那一节写的是"缺'这一下用闪避取消'这种写法，先记下，不做"。
- **教学轴模式要补的**：取消方式的写法（普通 / 闪避 / 大招 / 声骸 / 谐度破坏打断），谐度破坏按轴写的位置放，不自动插（§0 第 2 条）。要不要连帧数一起写，见 §10 第 6 条；我同意 Antigravity 的写法：默认只写取消方式，按最早合法帧执行；可选写局部帧，那一帧不合法就报错。

**转写也是一层读法。**
- **原文写的是按键**（a / e / z / q / r / 闪 / 跳），同一个键在不同状态下出不同的动作，比如椿的 E 是 E1 / E2 / E3，Z 在红椿里是烬华蔓舞。场景写成动作 ID 才确定（总设计 T6 补充）。
- **按键怎么对应到动作，现在记在 YAML 注释和确认清单里。** 例如 `m0-video-eq.yaml` 开头一大段"按键 → 动作"的说明和用户确认，人能读，程序和 agent 读不到。
- **建议**：场景的每一行能对回原文的哪几个记号、按什么读法。读法有疑问时，照 AGENTS.md 的约定另存只差一处的对照场景。

## 2. 底座的范围

| 层 | 内容 | 规模（2026-11-07 原型） | 怎么证明 | 进游戏吗 |
|---|---|---|---|---|
| 执行器 | 时钟、tick、调度、事件、结算 | 内核约 2,400 行（kernel、scheduler、switch、resources、triggers、buffs、enemy、formula、simulate、context） | 小用例、不变量、fuzz、conformance | 不用 |
| 共享规则 | 所有角色共用的：时停与顿帧、切人与切人锁、取消优先级、协奏 / 能量到账时机、buff 叠加与同帧先后 | 有限，估计几十条 | 每条一个对照实验 | 要，测一次全队受用 |
| 角色内容 | 角色、武器、声骸的数据与钩子 | 18 个模块约 3,200 行，随新角色增长 | 用到谁测谁 | 按需 |
| 场景 | 深塔、矩阵、具体敌人与环境 | 不属于底座 | 用来检验 | 按需 |

"底座做好"指前两层。第三层是内容库，永远不会"做完"，不进底座验收。这里"不验收"指的是不验收"角色内容是否符合游戏"；"钩子契约能被真实的角色模块用起来"仍要验收，用几个不同角色的机制组合覆盖（第四版补，采纳 Codex CD-08）。

**代码里的边界还没画出来。**
- **设计是分层的**：总设计 §2 把分析与展示定为第 ④ 层，§10 的目录写的是 `src/analysis/`。
- **原型混在一起**：轴搜索、排轴、套路卡、轴卡片、结论、敏感度、贴合度、调试表、配装对比、择优、矩阵、抽样、模糊测试、校准，这十几个分析模块和内核一起放在 `src/engine/`，合计约 2,900 行，比内核还多。
- **建议**：底座要被应用和 agent 直接调用，哪些是执行器的契约、哪些是建在它上面的分析，要在设计里写清。T12 说的"换语言时引擎约 3 千行"也应按这条边界来算。Codex 和 Antigravity 都同意这条边界；"保留现有执行器、把分析层切开"与"不必沿原型改"并不冲突（`codex_vs_claude/dispute.md` 第 2 条）。

**上层工具各自能证明什么**（第三版补，采纳 Codex §13.2）：
- **矩阵**：按每只 boss 单独仿真再接力，敌人状态在交接处不连续，回答不了"新 boss 出来那一帧的状态"；
- **择优**：完整仿真只证明所试候选在所选模型下的排名；
- **稳态的 `spread`**：是换统计窗口带来的变化，不是置信区间，也不含未知机制的误差。

**类比（作参考）**：给老游戏机写模拟器的人，也没有完整的官方资料，只有爱好者的笔记和一台真机。
- **商业游戏**：跑起来花不花屏，负责发现问题；
- **测试 ROM**：只问一件事的小程序，先在真机上跑出答案，负责定案。

对应到这里：教学轴和录像负责发现，训练场对照实验负责定案。

## 3. 规则的收敛

### 3.1 两种旋钮

- **数值旋钮**：帧数、倍率、能量值。调参收敛很好用。
- **规则旋钮**：A 读法还是 B 读法，比如 `rules.summonCountsAsChar`。它也能"调"，只是档位离散。

调参只在旋钮已经存在时有效。缺了旋钮时，调参会把误差塞进别的旋钮，看起来贴上了，其实是错的。好比地图少画了一座桥：调各段路的限速，也许能把这一趟的到达时间调对，换个目的地就露馅。

- **卜灵协奏**：段中的录像读数比仿真低。把"给多少"往下调，切走时就攒不满，切人从变奏变成普通切入，整局乱掉。问题其实在"什么时候给"（`replay-retro.md` §4）。
- **切人冷却**：全队共用的冷却调成多少帧，都模拟不出"切给别人不用等"。就像下象棋不知道"蹩马腿"，调"马能走几格"也模拟不出来。

缺旋钮的信号：
- **按下葫芦浮起瓢**：一处贴上了，另一处变差；
- **拟合出来的值很怪**：不是整数层，也不是游戏常用的整齐数；
- **差异有规律**：只在某种条件下出现。例如心的应世相低约 8%，只在有队友 buff 时出现，转相后消失（`replay-retro.md` §3）。

### 3.2 一条规则的生命周期

1. **发现**：现有旋钮解释不了的差异，或原文有两种读法。
2. **登记**：两种读法写成开关，缺省是现在的做法；每条推断有自己的名字。
3. **量影响**：翻过来改不改变结论。不改变的，先放着。
4. **看现有材料**：几份互不相关的录像、交叉数据源。
5. **设计实验**：事先算好每种读法该看到的数，选两种读法差得比读数误差大的条件。
6. **结局**：证实、否定或分不清；记下证据、适用版本、回归用例。

四点提醒：

1. **匹配变好只是线索。** 翻开关后匹配变好，可能是它对了，也可能是碰巧抵消了别处的错。`summonCountsAsChar` 翻过来，中 4 血条均方根差 2.37% → 1.61%，中 3 却 1.82% → 2.21%。"本质改进"要在几份互不相关的材料上都成立，定案靠实验。

   用来选规则的材料是建模证据，不是独立检验（采纳 Codex §5.2、§6.4）。焰痕那两个跳字（19482、9606）参与了选读法，就不能再拿它们证明读法对，要换一段没用过的材料再看。
2. **结局不只"证实"。** 否定的要留档，免得以后再提一遍，例如 TD-11 §5.2 的"切人退出盛绽"。分不清的，只要翻过来不改变任何结论，可以一直悬着。所以收敛的现实目标是：会改变结论的规则都定下来，不改变结论的允许悬着。

   "改不改变结论"要看问的是哪一种问题。`summonCountsAsChar` 翻过来，心队各轴的绝对数都降约 6%，但"哪条轴、哪套配装更好"一条没变（`assumption-sensitivity.md` 2026-10-28 的读法）。教学轴问的是"这条轴的上限是多少"，是绝对数，所以要收敛的规则比"比较两条轴"时多。

   结论也不只是 DPS（采纳 Codex §2.2、§6.3）：一条规则哪怕不改变 DPS 排名，只要改变了门槛（能不能变奏、能不能开大）、容错或某个动作必不必要，教学轴的解释就会变，也要优先。Antigravity v3 也把"会断轴、改变排名、显著改变绝对上限"并列为优先实测的标准。
3. **规则会随版本变。** `tys-video.yaml` 是 2025-11 的录像，当时游戏还没有谐度破坏，只能关掉（AGENTS 差异 29）。证实时要记下在哪个版本证实的。版本变了以后证据怎么处理，见 `claude-debate.md` CL-05（已 `done`）。
   - **旧证据保留**：旧观测作为当时条件下的证据保留，当前能否沿用另行评估；
   - **沿用不升级**：数据没变不等于机制没变，沿用不升级成"新版已实测"；
   - **版本分开记**：游戏版本、数据版本、运行代码三者分开记（见 §10 第 8 条）。
4. **一次只翻一个开关，不等于组合起来也稳**（第三版补，采纳 Codex §6.2、§6.3）。敏感度矩阵一次只翻一个开关。怀疑两条规则有交互时，要比"都没有、只有 A、只有 B、A 和 B 都有"四种情况，例如 B10：雷主超负荷与无归的谬误两条"全队攻击 +10%"叠不叠。只分别看 A 和 B，证明不了两者同时在时的规则。

## 4. 结果的可追溯性

### 4.1 两份清单

- **输入快照**：这次运行的全部开关、数据版本、轴，像程序启动时的全部环境变量。
- **依赖清单**：实际影响了这个结果的那几条。

"碰到"的定义是：翻过来，这里的决定会不同。依赖清单告诉调用者该翻哪几个，便宜；敏感度矩阵（真的翻过来跑一遍）告诉它差多少，准。

Antigravity 提议分两级记：读到开关的地方记 `rulesRead`（经过），分支真的因开关取值而分叉的地方记 `rulesDecisive`（起作用）。这正是 §4.3 第 5 条两种粒度的落地写法，我同意。

但"这一下依赖哪些规则"不能只沿因果链往上找。规则往往是通过时序、资源影响后面的事件，而不是通过"谁触发了谁"。这一点我写在 `claude-debate.md` CL-02。

**对外用四种名称，不宣称它们之间有包含关系**（第四版改，与 Codex CD-02 达成共识）。我在 CL-02 原来把"直接依赖"叫下界、把"起过作用的"叫上界，都不成立：局部起作用的规则可能被后面的等待吸收；没埋点的判断和装配期的选择会漏掉。

| 输出 | 承诺 | 不承诺 |
|---|---|---|
| 完整输入配置 | 本次选了哪些规则、数据与策略 | 每一项都影响了结果 |
| 执行观察记录（`rulesRead` / 局部的 `rulesDecisive`） | 某处读过规则，或在当时状态下改变了局部判定 | 改变了整局或某一下的结果 |
| 事件来源与数值输入 | 谁直接触发、用了哪些 buff 实例和公式因子 | 所有历史上的时序影响 |
| 指定反事实比较 | 换成列明的候选后，指定的事件、区间、指标怎样变 | 所有候选组合、所有场景都如此 |

跨运行时：
- **对应要有状态**：事件对应的结果分"对应明确 / 新增或消失 / 歧义 / 未分析"；另一条运行提前停了的，只能说"未执行到"。
- **重跑不能当成便宜**：敏感度矩阵 24 个场景 × 15 个开关用了 180 秒，平均每次仿真约 0.47 秒，按需重跑要在长轴上实测并缓存。

### 4.2 原则

- **原因在发生时记，不在事后推。** 好比每花一笔钱当场附发票，而不是月底看余额变化去猜。平时差不多，同一天花了好几笔就分不清了。
- **没发生的事也要能说明。** buff 该触发没触发时，要答得出"查过，条件没满足：超负荷 3 秒前就到期了"。录像里"无归的谬误的全队攻击没体现"这类问题，查的就是这个。
- **每条推断有自己的名字。** 能单独翻、单独追。
- **区分外部指定的状态。** 从某一帧起状态由外部指定（锚定视频轴的钉时刻、补满能量、指定失谐），结果里要标出来。

### 4.3 对照原型看到的差距

只作参考，不是改原型的清单：

1. **不是每条都能翻。** 假设表 40 条，有开关（`adjust.path`）的只有 14 条，其余要改代码才能翻。
2. **一个名字装了很多条。** `module-guess` 在 12 个角色模块里有 17 次 `ctx.assume` 调用，共 16 种不同的说明文字（卜灵的阵何时生成、守岸人的星域按人数升阶、渊武放完掀雷后锋芒清空……），共用一个名字，没法单独翻、单独追。第四版更正：莫宁两处调用记的是同一条读法，原来写成了"17 条"（Codex CD-05 指出，我核对过）。

   第六版再更正（Codex `claude-debate.md` CL-01 turn-2）：16 种文字也不等于 16 条独立的推断。例如心的一句说明里同时有"监听触发时立即出第一次""之后每秒一次""不计 18 帧出手时间"三点，它们可能分别被证实或否定。所以要按"能单独证伪的命题"拆，条数事先不定。
3. **一个开关管两条游戏规则。** `rules.forteKeepOnSwitch` 同时管心的照世相（`verify-guide` B1）和卜灵的卦象（B2）。这两项是分开测的，答案可能不同，但现在只能一起翻。
4. **碰到的记录按整局汇总，没落到具体事件上。** 汇总里是次数、第一次的帧和几个例子。说得出"这局碰到 X 共 12 次"，说不出"这一下伤害依赖 X"。
5. **"碰到"有两种粒度，现在混着用。**
   - **起作用才记**：`hitstop-in-global-stop`、`ult-no-switch`、`echo-input-priority`、`switch-ends-stop`、`wait-settled`、`summon-clock` 只在这条规则真的改变了结果时记，接近 §4.1 的定义；
   - **经过就记**：`dilation-rules`、`data-guess`、`stat-scaling-static` 是代码一经过就记，只是上界。
   - **第三版更正**：第二版把 `wait-settled` 错归为"经过就记"。核对代码后，它只在真的发生了"等就绪"时记（`scheduler.ts` 的 `closeSeg`），见 `claude-debate.md` CL-04。
6. **出处有一部分是事后推的。** 资源与伤害归到哪个动作，部分是跑完后按日志先后推出来的。`src/engine/trace.ts:233` 的注释写明：同一帧几个 buff 一起到期时，它们引出的事件会全算到最后一个头上。

   Antigravity 补了另一条错归路径：事件队列先进先出，E1、E2 先后入队时，E1 引出的事件写在 E2 之后，按顺序扫的人会把它认成 E2 引出的。
7. **事件之间的父子关系没进日志，但引擎其实知道。**
   - **日志里缺**：`buffApply` 不记是谁触发的，`judgmentSpawn` 不记由哪条事件生成，事件本身只有世界帧与战斗秒（`EventBase`），没有序号和相位。
   - **引擎里有**：事件队列处理第 i 条事件时，新产生的事件都是它引出的。`triggers.ts` 的 `bus.chain` 记着深度与起点，处理完就丢了。第四版补（Codex CD-04）：父事件是 `drain` 循环里的下标 `i`，`bus.current` 里的 `Link` 只有 `{ depth, root }`。不在 `drain` 里产生的事件（P3 时间线生成的判定、P6 到期的 buff、调度器开始的动作）另要写明来源（相位 + 原因 + 对象）。
   - **所以**：把这层关系作为已有事件的字段写进日志，第 6 条的两种归错就都没有了，不用另造一套系统。
   - **只加字段，不加新事件**（第三版补，采纳 Codex R05）：`drain` 把日志当成队列处理，钩子会收到每一条；加新事件会多触发钩子、改变事件链。
   - **延后生效的要带上来源**：判定、尾部这类在创建时就要记下来源，不能等生效时再找（Codex R02）。
   - **验收**：开关这项记录前后，业务事件、数值、报错、抽样结果都要逐条一样。
8. **没满足的条件没有记录。** 等待已经记了原因；buff 该触发没触发时，`triggers.ts` 的 `matches` 检查过但不留记录。三方都同意：这类诊断走只读查询或日志以外的单独记录，不往日志里写。
9. **资源变化记在两处**（第三版补，采纳 Antigravity 症结三）。命中给的资源写在 `hit` 事件的 `gains` 里，只有增量；其余写成 `resource` 事件，有增量也有变化后的值。不变量检查、汇总、调试表因此各自重放一遍资源。做状态查询、给 agent 用之前，要统一的是**读取视图**，不是业务事件（第四版改，与 Codex CD-04 达成共识）：
- **不改业务事件**：把命中资源改成另发 `resource` 事件，`drain` 会多处理一批事件、多调钩子；
- **统一视图从改值处采集**：在 `add` 实际改值的地方采集旁路元数据即可。

### 4.4 状态查询的边界（第三版补，采纳 Codex §3.2、§3.4、R04）

- **"这一帧的状态"要写明边界。** 建议 `stateAt(f)` 指世界帧 f 开始、P1 之前的状态；初始化（常驻 buff、`onResolve` 及其事件）完成、第一个 tick 之前记作 S[0]。
- **同一帧里也有先后。** 满协奏切人的那一帧，切出者的协奏还没清零，要等切入者的变奏走到延奏触发帧才清零（TD-05 §4.2，`tests/td05.test.ts` T05-2）。
- **日志的先后不等于钩子看到的状态。** `actionStart` 先写进日志，之后才扣能量、处理事件队列，所以钩子处理 `actionStart` 时看到的已经是扣过的能量。
- **展示轨道不是完整状态。** 共鸣回路说明、冷却轨道在 P6 采集。完整状态像能续跑的存档，包括：前后台的动作与局部帧、飞行中的判定、尾部、buff 实例与内置冷却、钩子的 `vars`、敌人状态、膨胀窗口、调度游标、事件队列的簿记、RNG。
- **第一版靠重算。** 从相同输入重算到指定边界，返回与运行隔离的拷贝；之后再考虑快照与续跑。

### 4.5 报告与比较层也会丢东西（第三版补，采纳 Codex R03、R09–R11，Antigravity 症结五）

这几条都是纯软件问题，用小用例就能推进，不用进游戏。我读代码确认了下面描述的代码路径；人造场景的复现是 Codex 做的。

- **同名 buff 两人各给（R09）。** 运行时按（定义、持有者、目标）分得开，但日志的 `buffApply` / `buffExpire` 不带提供者，覆盖率按"buff→目标"合并（`summary.ts` 的 `buffUptime`），第一份到期就把统计关掉了。
- **打死几倍血（R10）。** 击杀分数用"血量 ÷ 击杀时刻"，分项拆解（`analysis.ts` 的 `dpsBreakdown`）按 `[lo, hi)` 取命中，致死那一下正好在右端被排除。还要分清"含溢出的伤害"和"有效扣血"。
- **没跑完（R11）。** 指令都发完了、但最后一个动作还在放时到了帧数上限，只记一条警告、不报错（`scheduler.ts` 的 `runLoop`），截断的窗口照常进入比较。没打死时的外推状态，在比较口径、对比、搜索里也丢了。所以"没有 `error`"不能当成"结果完整"。
- **录像贴合（R03 与 Antigravity 症结五）。**
  - 录像动作找 10 秒内最近的同名动作，不是一对一，两条观测可以对上同一下；
  - 锚点全部失配时得 0 分，"没有可比的数据"被当成了"完美"；
  - 单下跳字没算进去；各项按公开的 `FIT_WEIGHTS` 折成秒再相加（第四版更正：原来误写成"直接相加"），加权和会掩盖覆盖与冲突，变奏 / 普通对不上（`typeMiss`，每次 2 秒）也能被别的项抵掉，应单列为冲突；
  - 翻规则开关和改轴动作的候选混在一张榜里排；
  - 改进的方向（与 Codex CD-06 达成共识）：
    - 先定比较状态与实例对应，再看各通道的残差与覆盖；
    - 没有有效观测时"不可评估"；
    - 观测集合固定，丢掉难匹配的动作不能让分数变好；
    - 分数只用于排序。

## 5. 信源：按字段类型看，不按网站看

| 字段 | 现状 | 怎么对待 |
|---|---|---|
| 倍率、基础属性 | 与 Wuthery 解包核对：当前角色与声骸已连接的伤害条目 2681/2681 倍率一致 | 基本可信 |
| 帧数 | 公开解包里找不到逐项基准；WuwaLAB 143 个有伤害的动作对上 111 个，各项都一致的 48 个，且它的帧含顿帧 | 线索，靠录像与实验复核 |
| 语义：备注、空格子、"下落"行、技能文字 | 只能人读 | 风险最高 |

影响最大的几次修正，多是读法或共享规则出了错，不是数错了：

| 修正 | 错在哪 | 影响 | 出处 |
|---|---|---|---|
| 雷主大招的全局时停丢了 | 类型格空着，没读出来 | 心队原轴稳态 48,470 → 54,322（+12%） | AGENTS 差异 3 |
| 心转相第 254 帧的优先级 | 变化帧写了，新值空着 | xin-team +6.5%，轮椅 +8.7% | 差异 43 |
| 声骸起手的优先级 | 共享规则缺失 | 多数场景 +2%～8% | 差异 21 |
| 椿 E2 的落地段 | 帧从落地算，没后移 | M0 视频轴 −3.8% | 差异 4 |
| 切人冷却每人单独计 | 共享规则理解错 | 5R18Z +3.7% | 差异 18 |

数错也有过（段数、个别倍率连错，4 个声骸冷却），但影响小，交叉核对就能查出来。所以主要风险在读法。

做法：每修一个错，都问"全库还有几处同样的写法"，再做成 flag。`landingUnshifted`、`priorityValueMissing`、`dilationTypeGuess` 都是这样来的，这一步应该固定下来。

**AI 整理的资料也只是线索，它标的置信度不是证据。** 两个实例：
- **协奏到账时机**：`m3-verify-answers-gemini.md`（2026-10-02 提交）里，"协奏第 1 帧（出手时）给全额"标的可信度是"高"，引的是 NGA 帖子。第二天用户实测是逐段按命中给（TD-06 Q1，2026-10-03 关闭）。
- **散华那一段的顺序**：M0 视频轴原文和 Gemini 核对过的都是 EZR，用户后来指出应为 ERZ（`m0-confirm.md` V5）。

`~/wuthering-waves/` 里的文字轴也是 Gemini 整理的，和作者的流程图有出入（`video-input-guide.md` §2）。这和"让多个 AI agent 评审""让 agent 当底座的使用者"都直接相关：AI 产出的结论，要和数据表、实测一样记下来源种类，不能因为它写得笃定就当成定论。三方评审本身也是 AI 产出，所以合成总体设计前，技术断言要核到代码（`claude-debate.md` CL-04）。

**消掉 flag 不等于证实**（第三版补，采纳 Codex R12）。

## 6. 差异的收敛方法

1. **先验尺子。** 确认配装、时钟、比的是哪一下。尺子自己也会错。

   **一轮时长的时钟是契约冲突**（第三版按 Codex R01 改了定性），不是单纯的代码错：
   - **注释写世界秒**：校准点 `kind: loop` 的 schema 注释（`src/data/calibration.schema.ts:23`）与 `calibration/README.md` 写的是世界秒；
   - **取值是战斗秒**：实际取 `span.endT - span.t`（`src/engine/calibration.ts:21`），日志里的 `t` 是战斗秒（`kernel.ts` 的 `log`：`t = battleFrames / 60`）；
   - **TD-11 也说战斗秒**：TD-11 §1.2 写的是"X 秒一轮"一般指战斗秒。

   两种时钟都有正当用途：按视频时间量的是世界秒，深塔倒计时量的是战斗秒。所以修法是让每个观测写明自己的时钟（Antigravity 提议加 `clock: world | battle`），而不是把一边改成另一边。

   跳字也要写明比的是不暴击、暴击，还是不知道（`unknown`）。现在是自动挑接近的那一支，只能找到相容的解释，证明不了那一下确实暴击了（Codex R06）。不知道的不能缺省填成暴击，两支都列出来（第四版补，Codex CD-06）。
2. **读已有录像和日志时，顺着因果往下查。** 先对时序，再对资源、状态、单下跳字，最后看血条。上游错了会带歪下游，就像编译报错要先修第一条。录像动作要先一对一对上，再看误差（Codex 第 2 步）。
3. **用最贴身的尺子。** 中 4 里心的直接伤害偏低、踏月归心偏高，一抵消血条只差 2.4%（`replay-retro.md` §3）。血条贴合不等于机制对，跳字最锋利。
4. **先写预测，再去测。** 列出候选读法，算好每种该看到的数，避免事后硬凑。
5. **允许不归零。** 修好、定案、缩小范围、分不清、超出模型都是结局。分不清就保留开关，并在结果里标出来。
6. **进训练场定案时反过来，自下而上隔离**（第三版补，采纳 Antigravity §5）。读录像时所有变量缠在一起，所以从上游往下查；做实验时可以人为切断上游。

   下面几级是可选的工具，按问题选用，不是每个问题都要走完（第四版改，Codex CD-07）。只问"切走保不保留卦象"，看状态就够了。切人处把时间归零，只能隔离累计的时间偏移，消除不了继承下来的能量、buff 和飞行中的判定。几级是：
   1. 单人裸打，对面板和跳字；
   2. 逐个加 buff 看比值，怀疑交互时做四种组合；
   3. 看单次上场的资源收支：资源从低处起，看命中前的读数；
   4. 按切人边界分段，比动作间隔。

   每一级对上了，只说明这一级在所测条件下成立，不自动推广到别的情况（Codex §2.2 对"一次对上就永久锁死"的修正，Antigravity v3 已接受）。
7. **用比值找乘区**（第三版补，把 Antigravity §5.1 当作方法采纳）。
   - **比值相同**：同一时刻、不同伤害类型的偏差比值相同，差异多半在乘法项（攻击、加深、防御抗性）；
   - **比值不同**：比值不同、而且能用各自的增伤底数解释，差异在加算的增伤区；
   - **分段回落**：比值随时间分段回落，是几条 buff 先后到期。

   心第 1 轮的比值是 1.083 / 1.077，之后 1.031 / 1.036，最后 1.000。用原始跳字解（第四版，Codex 与我各算一遍，结果一致）：两类伤害共有一个乘数 m ≈ 1.044，另少算一项增伤 b ≈ 0.119。

   **第五版：按当前代码重做后，这个案例拆成了三块**（详见 `antigravity-debate.md` D-AG-03 的 Claude turn-1）。
   - **跳字表的仿真列过期了**（Antigravity 指出，我实跑核实）：镇寰宇在表里是 195,198，当前代码是 180,256，因为 `镜影流电之瞬.5延奏` 在它命中前 18 个战斗帧已到期。第四版拿旧值做的"后段对上"作废。
   - **b 极可能是配置差异**：把雷主首位从天演溯心换成绝息魄（"放延奏后下一个变奏登场的角色导电 +12%，15 秒"），零个可调参数，两类伤害的残差就变成同一个数 1.0437，照世·E-2 从 1.031 变成 1.000。扫描不记槽位，首位是按列表顺序推的，要请用户确认。
   - **镇寰宇那一下还是对不上**：若按候选 B-1（两条 15 秒的 buff 在变奏入场时一起挂上），录像的比值要求镇寰宇时两条都还在（1 + 0.369 / 3.016 = 1.1224，录像 1.1222）；而当前仿真里它们比镇寰宇早 18 个战斗帧就到期了。

     第六版收窄（Codex D-AG-03 turn-2）：
     - **2 帧是仿真算的**："两下之间只走了 2 个战斗帧"是当前仿真的输出，不是从录像读出的游戏战斗帧；
     - **钉点晚只是线索**："钉点晚了约 0.4 秒"只是一条线索，要先对上同一次起手 / 命中、核对锚点与测量误差，不能直接归因；
     - **只排除了一个具体设定**：我原来说"b 按世界时钟计时"的候选被排除，其实排除的只是"变奏入场时触发、按世界时间计 15 秒"这一个具体设定；按世界时钟计时这一类没有被排除，只是缺少来源、优先级低。
   - **m ≈ 1.044 仍未知**：在战斗帧 1587 之后、1728 之前消失；仿真里超负荷、隐世回光早已在场，所以不是漏了它们。区分办法是看心的面板，以及已有录像里同时段队友的跳字比值。

   B10（两条全队攻击 +10% 叠不叠）若"不叠"成立，游戏会比仿真低，方向与 m 相反，所以要和这个问题分开设计。

   **教训**：对照表里"录像"一列是固定的观测，"仿真"一列随引擎版本变，要由命令生成、记提交号；台账引用仿真值时也要带版本。
8. **读数本身有精度**（采纳 Codex §3.4、§7）。录像 30 帧、剪辑过、HUD 刷新有延迟时，秒数乘 60 得不到逐帧精度。期望伤害也不该要求逐下等于录像里的那一次；挑一个最贴合的随机种子，验证不了机制。

**完整例子（只差最后一步）**：
- **现象**：踏月归心仿真约大 2 倍。
- **候选**：阵算不算角色，也就是给不给心叠霆心域。
- **录像判不了**：见 §3.2 第 1 点。
- **实验**：B11 约 3 分钟，看开阵后 6–8 秒内霆心域是每下冲击波 +2，还是不涨。
- **价值**：翻过来，心队教学轴约 −5.6%～−6.2%（`tower-20261026.md` 中 4 第 8 条）。

## 7. 实测成本

从文档看到的情况（是推断，可能有测过但没记的）：

- `verify-guide.md` 共 21 项，手册估算合计约 47 分钟，没找到这些项的回答记录。
- `docs/calibration/points.yaml` 有 37 个校准点，`game` 都还空着。
- 录像剖析投入很大（中 3 场景写到第五版），`replay-retro.md` §0 认为它定机制的效果在变差。
- 2026-10-03 那批实测关掉了 TD-06 Q1、Q2、Q4 与 TD-07 Q3，说明对照实测本身很管用。

所以瓶颈可能不是"实测太多"，而是力气花在了读录像上，或者进游戏这一步摩擦太大。降成本的办法：

1. **只测会改变结论的。** `pnpm sensitivity` 能回答哪些规则会改变结论。共享规则优先，测一次全队受用。
2. **打包测。** 一次进游戏测 5 项左右，事先算好每种读法的预期数字，只管打和交视频。手册里的分钟数只是操作时间，换号、重置、重录、读数与入账另计（第四版补，Codex CD-08）；A 类、B 类在 everbird 账号，C 类在 Evariste 账号，要按账号分两次。
3. **只记录，不操作。** 跑轴记录插件（`okww-axis-notes.md` §2）能省掉一部分读帧。让工具自动操作游戏跑实验，可能有账号风险，不建议先走这条路。

底座的验收分两级（采纳 Antigravity D-AG-01 的拆法，合并了 Codex 和我的标准）：
- **第一级，执行器与工具链自洽**（软件侧，Codex 的标准）：
  - 执行器的检查全过，S1 的几项修好；
  - 支持范围内的状态可查、关键事件可解释；
  - 已解的真实案例（散华 E、焰痕）和一个分不清的案例（卜灵协奏时机）都走完一遍；
  - 每份输出都带输入快照与依赖清单。
- **第二级，共享规则基线**（机制侧，我的标准）：影响为大、中的共享规则都有定论，也就是证实、否定或明确分不清，并写成回归用例。

**第四版修正（与 Codex CD-08 达成共识）：两级都要写明用途和覆盖范围。**
- **"诊断记录完成了"不等于"可以发布精确结论"**；

  - "散华重击一松手就切维里奈"的精确切人帧（依赖 `burst-release`）。

   - **进展（倾向共识）**：以内核里的规则分支为锚，对照 TD 与假设表。放在哪、用什么格式，见 CL-01。
5. "一能按就按"包不包括 §1.5 那三种按意图推出的等待（变奏切人等出手、空中入场等跳起、出场技等后台走完）？包括的话写进教学轴模式的规格；不包括的话，要求轴里写明。

6. 取消怎么写：只写"用什么取消"，由引擎算最早帧；还是像 WuwaLAB 那样连取消帧、切人帧一起写？前者贴近"一能按就按"，后者能直接复现作者的手法。
   - **进展（倾向共识）**：默认只写取消方式、按最早合法帧；可选写局部帧，那一帧不合法就报错。
7. 规则开关的粒度：一条游戏规则一个开关（可以按角色、按动作），还是允许一个开关管一类？§4.3 第 3 条是现在的反例。
   - **进展（倾向共识）**：一条能单独证伪的游戏事实一个开关。
8. （第三版新增）游戏版本更新后，已有的证据和已定案的规则怎么处理？见 CL-05。
   - **第四版**：与 Codex 在 CD-05 达成共识，内容如下：
     - 台账按"命题、候选、证据条目、当前结论"组织；
     - 证据挂在候选与条件上；
     - 沿用旧版证据要标明，级别不提升。

     三条真实案例的试填见 CD-05 的 Claude turn-1。还剩一个强调点：不确定的规则至少写出替代候选，能不能运行按影响排期。
   - **第六版（`claude-debate.md` CL-01、CL-05 已 `done`）**：
     - **候选的写法**：强调点按 Codex 的修正定稿：写出已知的替代候选；不知道还漏了什么的，记"候选未列全 / 待解释"，不为凑表格编一个备选。没有运行时开关的候选照样入账。
     - **`TrackedId` 能保证的**：保证引用的 ID 存在，生成文档减少重复维护；不保证规则含义正确、所有分支都登记了。
     - **版本分三种身份**：
       - 观测对应的游戏版本、日期与条件；
       - 数据材料的版本（xlsx 文件名日期、SHA-256、资源版本）；
       - 运行用的代码与输入。

       不同身份的版本号不能直接比大小。
     - **自动复核还没有**："按数据变化自动标需复核"现在不存在：构建只核对哈希、输出计数，没有"变化的字段 → 受影响的规则"这一步。正式设计里要写成待实现的能力，原型先对高影响规则人工维护引用。
9. （第三版新增）合成总体设计前，各评审里的技术断言怎么核对？见 CL-04。
   - **第四版**：Codex 同意断言要有可核对的依据，但反对把"另一 agent 签字"变成原型进展的门槛。我说的范围是"合成总体设计这份文档时作为决定依据的断言"，待 Codex 确认（CD-08 第 3 点）。
