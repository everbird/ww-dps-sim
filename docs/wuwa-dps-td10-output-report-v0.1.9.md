## 0. 要点

1. 所有数字都从事件日志派生（总设计 §3.5），不在别处重算。
2. **稳态取完整的轮**：第 2 轮到倒数第 2 轮。第 1 轮受开局资源影响，最后一轮没有下一轮的边界、偏高（§2）。
3. **对比**：把场景改几处、各跑一次再做差；有分轮时比稳态，"差在哪"按窗口内的**每秒伤害**拆到角色与动作，再看 buff 覆盖率与面板（§3）。
4. **副词条边际**：每种副词条各加一档（缺省各档平均）、重跑比稳态 DPS（§4）。轴是固定的。

## 1. 汇总 `Summary`

| 字段 | 含义 |
|---|---|
| `totalDamage`、`windowFrames`、`dps` | 统计窗口内的总期望伤害、窗口长度（战斗帧）、DPS = 伤害 ÷ 窗口秒数 |
| `overflowDamage` | 窗口外仍在结算的伤害（残留的领域、召唤物），不计入 DPS |
| `byChar`、`byAction` | 窗口内按角色、按动作（角色 + 动作 ID）的伤害与占比。按动作是按**判定所在的动作**（xlsx 的组）：散华重击居合引爆的"E-引爆冰棱"算 E，"大招-引爆冰川"单独一行；对照 xlsx、`pnpm compare` 都用它。时间轴网页里动作的伤害另按引发的动作算（v0.1.6，§5.1） |
| `resourceTimeline` | 每 `rules.sampleInterval` 个世界帧采一次三人的能量与协奏（TD-06 §6.1） |
| `buffUptime` | "buff→目标" → 窗口内存在的比例（TD-07 §10.1） |
| `waits` | 不是写轴要求的等待（TD-09 §3.3） |
| `warnings` | 装配与仿真中的提示；v0.1.6：含写了"变奏"的切人没变奏（code `introMissed`，TD-09 §3.5） |
| `perLoop?`、`steady?` | 分轮与稳态（§2，`options.repeat ≥ 2` 或有启动轴；v0.1.2：启动轴是第 0 轮，记为"启动"） |
| `enemy`（v0.1.1） | 窗口内失谐、谐度破坏命中、白条打空的次数，与谐度破坏的伤害（TD-06 §14） |
| `skipped`（v0.1.1） | 跳过的可选指令（排轴里写了 `?`，TD-09 §3.2）：第几轮第几条、原因 |
| `assumptions`（v0.1.5） | 这次碰到的假设（总设计 T16）：编号、次数、第一次的战斗帧、几个例子，按假设表的顺序；每次都适用的（不 tracked）不列，见 `pnpm assumptions` |

**统计窗口** = [第 0 帧, 最后一条指令的完成时刻)（TD-09 §3.9），按战斗帧；`options.endAt` 可覆盖。战斗帧 < 窗口终点的伤害计入，其余是窗口外。

## 2. 分轮与稳态

- **每一轮** = [本轮 `loop` 事件, 下一轮 `loop` 事件)；最后一轮到统计窗口终点（TD-09 §3.7：等下一轮起手的时间算在上一轮里）。
- `perLoop[k]`（v0.1.4：只列窗口内开始的轮；`endAt` 截在某一轮中途时，之后的轮不列）：`loop`、`start`（战斗帧）、`frames`、`damage`、`dps`，三人的 `energyDelta`、`concertoDelta` = 下一轮开始时（最后一轮：窗口终点）− 本轮开始时。资源按日志从初始值重放（同 `resourceTimeline`）。首尾差都是 0 说明这条轴能自给。
- `steady`：第 2 轮到倒数第 2 轮合起来的伤害 ÷ 时长（`from`、`to`、`frames`、`damage`、`dps`）；只有 2 轮时取第 2 轮。对比口径的窗口（`basisOf` 的 `lo`）按轮号找第 `from` 轮的开始（v0.1.4；原来按 `perLoop` 下标取，有启动轴时错成第 1 轮，分角色、分动作、buff 覆盖率与择优的快速重算都偏了一轮，稳态 DPS 本身不受影响）。
- **启动轴**（v0.1.2，TD-09 §3.7）：场景写了 `opening` 时，它是第 0 轮（"启动"），照样列进 `perLoop`；稳态只看循环轴的轮（第 2 轮到倒数第 2 轮；循环轴只有 1 轮时没有稳态，只给 `perLoop`）。
- **为什么不取最后一轮**（总设计 v0.1.5 原写"稳态以最后一轮为准"）：最后一轮没有下一轮的边界，等能量、等冷却、轮首的 `wait` 都算不进来，DPS 偏高。M0 代表轴循环 4 轮（v0.1 时）：第 1 轮 25,238，第 2、3 轮都是 26,061（资源首尾差 0），第 4 轮 26,722。M4 之后（v0.1.1，带谐度破坏与破盾）：第 1 轮 27,965，第 2、3 轮都是 28,939，第 4 轮 27,123（第 4 次失谐时轴已放完，没有谐度破坏）；第 2、3 轮椿的能量首尾差 ±4.3，是破盾回能落在第 2 轮。谐度破坏按 xlsx 附页2 调整后（v0.1.2：谐破冷却 4C 3 秒、按钮、不拆连段）：第 1 轮 27,965，第 2、3 轮 29,367 / 29,369，第 4 轮 30,032。椿首位换梦魇·无冠者、Q 挪位后（v0.1.3，AGENTS.md 差异 3）：第 1 轮 29,878，第 2、3 轮都是 31,023，第 4 轮 29,079（每轮 31.77 秒，最后一轮 32.48 秒）。
- **写法**：轴的结尾要回到第 1 轮开头的局面（M0 代表轴结尾 `switch 维里奈`），`options.repeat` 4 左右、`maxFrames` 相应放大。

## 3. 对比 `compareRuns`

**口径** `basisOf`：有分轮取稳态，否则取整个窗口；记为 [lo, hi)（战斗帧）。

**差在哪**：

| 项 | 怎么算 |
|---|---|
| DPS | 对比 − 基准，及百分比 |
| 分角色、分动作 | 窗口内的**每秒伤害**（伤害 ÷ 窗口秒数），同一个窗口里加起来就是 DPS；两边窗口长短不同（换了声骸、轴变快）也能比。按差额绝对值排序 |
| buff 覆盖率 | 各自的窗口内算（`buffUptime(log, lo, hi)`），标记型 buff（计时、状态）不列 |
| 面板 | 攻击、暴击、暴伤、共鸣效率（含常驻的共鸣效率 buff）；常驻的其他 buff 在命中时才叠，不在面板里 |

**命令**：`pnpm compare 基准.yaml 对比.yaml`。打印两边的口径与 DPS、差额，变化了的面板，分角色、分动作（差额前 12）、buff 覆盖率（差 ≥ 1 个百分点，前 12）。场景有错或运行出错时退出码 1。

例（2026-10-05，v0.1.3）：视频轴 `scenarios/m0-video.yaml` 一日花前的补位 `A1~ A2~` 换成固定打两下 `A1 A2`，稳态 DPS 30,458 → 31,312（+2.80%），两边每轮都是 27.15 秒：这条轴有空余，多打的 A 不占时间。差额几乎都在椿：延奏每秒 +672（固定两下时每次切走都还在含苞里，延奏都打含苞 + 含苞追加；补位时有一轮切走时含苞已结束，只打普通版）、A2 +164。

旧例（v0.1.2，M0 代表轴当时的配装）：椿首位异相·无妄者换梦魇·无冠者（词条不变），稳态 DPS 29,368 → 32,706（+11.4%）：首位加成湮灭 / 普攻各 +12%（覆盖率 0 → 100%），它的 Q 只要 39 帧（无妄者 123 帧）；轴变快后失谐落到维里奈在前台的时候，谐度破坏从椿放变成维里奈放。代表轴 2026-10-05 已换上用户实际的无冠者（词条不同、Q 挪位，稳态 31,023），这个例子不再对应现在的场景。

## 4. 副词条边际 `marginal`

- **一档**：`echo-stats.json` 的 `subTiers`（TD-01 §12.6），缺省取各档平均（比例取到 0.0001，固定值取整：暴击 8.4%、暴伤 16.8%、攻击% 9.0%、攻击 +50、生命 +450…），`--tier max` / `min` 取最高 / 最低档。
- **加在哪**：该角色**最后一件声骸**的副词条上（不动首位；场景必须至少有一件声骸）。
- 13 种副词条各重跑一次，按 DPS 增加从大到小排。
- **轴是固定的**：共鸣效率只在原来要等能量时才有收益；"效率够了能把轴排得更紧"要改轴，属于轴搜索（总设计 M7）。只影响队友 buff 的角色（维里奈），自己的副词条收益很小是正常的。
- **命令**：`pnpm marginal 场景.yaml [--char 角色] [--tier avg|max|min]`，不写 `--char` 时三人都算。M0 代表轴（4 轮）每次约 0.3 秒，一个角色 14 次。
- 例（2026-10-05，M0 代表轴，椿，v0.1.3 重算）：暴伤 +5.59% > 暴击 +4.31% > 攻击% +2.58% > 普攻加成 +2.13% > 攻击 +1.38% > 共鸣解放 +0.33%；共鸣技能、重击加成为 0（她的 E、重击打的是普攻伤害），共鸣效率为 0（这条轴不等能量）。换上主词条暴击 22% 的无冠者后暴击已到 90%，暴伤反超暴击（v0.1.2 时暴击 +5.73% > 暴伤 +4.21%）。

### 5.1 时间轴网页（v0.1.2，M6 第一步）

- `web/timeline.html` 是模板：一个文件，自带样式与脚本，不用构建；直接打开时可以选 `pnpm sim` / `pnpm timeline` 写出的 JSON。
- `pnpm timeline 场景.yaml`（`src/cli/timeline.ts`）跑完仿真，把结果与画图要的元数据（队伍、能量上限、敌人量表、排轴原文（含启动轴）、各动作的类别）嵌进模板，写 `out/<场景名>.html`；`--fragment` 不带 `<!doctype>` 与 `<head>`，给要再包一层的地方用。场景出错时网页照样写出，日志保留到出错为止。
- 画的是事件日志本身：各角色的动作条、能量与协奏曲线、buff 区间、敌人的偏谐值与白条（`hit.enemy`，TD-02 §7.3）、失谐 / 谐度破坏 / 破盾的标记，与 §1、§2 的汇总。
- v0.1.3：**调试表**——网页下方跟着"范围"选的轮次（缺省稳态第一轮，没有稳态时第 1 轮）显示分段、逐条与资源逐步表（与 `pnpm trace` 同一份数据：`timelineModel` 多 `trace`，每轮一份），点一行在时间轴上高亮那一段并滚过去。场景有 `video` 时多一行"视频对照"（△ 按视频推算的位置、● 仿真里的位置，连线红 = 本段仿真慢、绿 = 快；`timelineModel.video`），调试表多视频、累计差、本段差三列（TD-11 §6.3）。
- v0.1.6：**出处**——`timelineModel` 多 `gains`（每个动作给的资源，按出处合计：`src/engine/trace.ts` 的 `actionGains`）、`effectInfo`（资源型效果的原文）、`energyShare`（能量的分配比例）；日志里的命中带 `owner`（归到的动作开始的实例号）、`trigger`（钩子在命中后生成的判定：由谁的命中触发）、`via` 与 `note`（引出原因）。归属规则是"谁引发的算谁"（`walkOwners`，TD-11 §6）：重击居合引爆的冰算重击居合，维里奈的协同攻击归她自己的动作（伤害仍算维里奈）。各视图怎么显示见 TD-12 §2.1；原版时间轴的命中提示写引出原因，表格区最前面列"轴可能有问题"。
- v0.1.7：**检查器的数据**——`timelineModel` 多 `resources`（每人每种资源的逐帧值：`resourceTracks` 按 `gainSteps` 重放，只列有变化的核心资源槽，[世界帧, 值]）、`forte`（`SimResult.forte`：角色模块的只读显示钩子给的共鸣回路状态，变了才记，TD-08 §3.1）、`cooldowns`（`SimResult.cooldowns`：每个 tick 结束取，"从第几战斗帧起能用"变了才记，倒计时与全局时停里不变；按次数充能的另记还剩几次）。这三样都不进事件日志，一致性样例不比。视图 D、E 的检查器用它们（TD-12 §2.1）。
- 排轴编辑、场景编辑留给 TD-12。

## 6. 结论 `insight`（v0.1.5）

同一个场景改一处、多跑几次，推出几条能直接用的结论（`src/engine/insight.ts`；命令行 `pnpm insight`，网页"结论"页）。全部按期望值算；比较口径同对比（有分轮取稳态，否则整个窗口，§3）。M0 代表轴一次约 25 次仿真、3 秒。

**① 共鸣效率需求**：轴里放大招的每个人，"窗口里不因大招能量等待"最低要多少共鸣效率。改的是静态面板（常驻的共鸣效率 buff 不变，报的数是面板 + 常驻 buff，同 `pnpm sim` 的显示）；先看现在够不够，再在 [100%, 现在] 或 [现在, 现在 + 200%] 里二分，精确到 0.25%。按"共鸣效率越高越不用等"的单调假设二分，得到的是近似值；加到现在 + 200% 还要等，报"大招放得太早"（`need = null`）。富余的部分可以换成别的副词条——这关闭了 §8 Q2。v0.1.7：另报下限 `EnergyNeed.floor` = 面板 100% + 常驻共鸣效率 buff（最低能压到多少）；最低等于它时命令行写"下限：…，不堆共鸣效率也够"，网页标"（下限）"。M0 代表轴（2026-10-17）：椿 153.2% → 最低 125.6%（下限：千古洑流常驻 25.6%），散华 170.2% → 110.0%（下限：轻云出月 2 件 10%），维里奈 265.8% → 194.7%。注意：轴里给大招补了位的（心 · 雷主 · 卜灵的心，万阙垂天前补照世普攻），大招从不等能量，①看不出要求，代价在补位的时间上（docs/xin-conclusions.md §1.3）。

**② 操作容错**：每个决策点（切人、不是连段后续的出招）在合法之后都再晚 N 帧执行（`options.inputDelay`，TD-09 §3；等待原因 `input`，不计入 maxWait、不进 `Summary.waits`）。连段的后续（有 `comboFrom` 的动作，如 A2–A5）按玩家会预输入不加；写轴的 `+N` 先算，再加操作延迟。缺省看 0、3、6、10、15 帧的 DPS、变化与每轮时长；某个延迟下跑不通（如派生窗口过了、连段断了）照实报出。M0 代表轴：3 帧 −2.9%，6 帧 −9.5%，10 帧 −14.7%，15 帧 −19.3%（每轮 31.8 → 37.1 秒）。这是确定性的扫描；随机的抖动见抽样模式（总设计 T4）。

**③ 假设敏感度**：假设表里给了 `adjust.path` / `values` 的条目逐个翻一下（总设计 T16），报 DPS 变化。v0.1.7：tracked 的假设只翻这次仿真碰到过的，没碰到的翻了也一样、不跑，列进 `Insight.notHit`（命令行与网页各一行"这次没碰到、翻了也一样"）；异常效应两条可翻：`rules.effectTickReset = true`（`effect-tick`）、`rules.effectOwner = first / onField`（`effect-owner`，TD-06 §18.6）。M0 代表轴：`options.inputDelay = 6` −9.5%，`options.tuneBreak = off` −9.0%（这一项量的是谐度破坏的贡献）；`def-no-floor`（没有减防）、两条异常效应的假设没碰到。心 · 雷主 · 卜灵修复轴：`effectTickReset` −3.10%，`effectOwner` −0.13% / +0.09%。

**⑤ 抽样（总设计 T4）**：`sampleRuns`（`src/engine/sample.ts`，命令行 `pnpm sim 场景 --sample N [--seed S] [--jitter F]`）按不同种子跑 N 次抽样模式——逐段抽暴击，`jitter > 0` 时每个决策点的操作延迟另加 [0, jitter] 帧的均匀抖动——报比较口径下 DPS 的平均、标准差、最低 / 5% / 中位 / 95% / 最高，与期望值的差。每次的种子从总种子起的一个流里依次取（`runSeeds`）；汇总按每段抽到的暴击 / 非暴击计（`hitValue`）。M0 代表轴 300 次：只抽暴击时平均比期望值 −0.01%（期望值就是精确值，没有"暴击时触发"的反馈），标准差 3.1%，5%–95% 在 29,158–32,173；加 0–6 帧抖动平均 −3.9%。现在只是研究工具：时间轴、调试表、对比、择优仍按期望值；操作失误（漏按、闪避失败）以后再说。

**④ 指令被挡住的时间**：窗口里队首指令在等什么，按原因合计秒数与占窗口的比例，各列最长的三段。写轴要求的（`+N`、`wait`、`at`）、操作延迟、正常出招节奏（派生窗口、优先级、连段、同一 tick）不算；挡住时前一招可能还在打，不等于角色空闲。M0 代表轴：等前一招出手 14.5 秒（22.9%，主要是椿 A4 → A5，总设计 §13"等就绪"）、输入锁 4.4 秒、等冷却 0.03 秒。

### 6.1 轴搜索 `searchRotation`（v0.1.8）

从一条现成的轴出发做局部搜索（`src/engine/search.ts`，命令行 `pnpm run search`——要写 run，pnpm 自带的 `search` 是搜 npm 包；总设计 §3.7 的第一版）：在循环轴上改一处，完整仿真打分，按比较口径（同 §3）排名。用途是检验与启发：比原轴好的改法是"游戏里也该更好"的假设，要拿实战核对；反过来，实战里明显更好的打法在这里排不上去，说明模型漏了什么。

- **候选**：挪动（move）——把一个动作挪到同一角色别的位置（同一行或这个角色的其他行），缺省只挪首位声骸技能（`Q`、`Q·…`），`--move` 改成别的动作名；去掉（drop）——`--drop` 列出的动作逐个试着去掉，行空了就去掉这一行。v0.1.9 另有两种（都是"另外试"，缺省仍只挪 Q）：对调（swap，`--swap`）——同一角色相邻的两个动作对调（同一行相邻的，或行末与紧接着的同一角色那一行开头；两个都是补位、或写法一样的不试）；插入（insert，`--insert A1~,谐度破坏?`）——按轴里的写法（可带后缀）插进去，只插给有这个动作的角色，每行每个位置各一种，没人有这个动作时报错。只改循环轴（`rotation`），启动轴不动；`--char` 只改这些角色的行；后缀（`!`、`?`、`~`、`+N`）跟着动作走。
- **打分**：每个候选只重新编译循环轴（`compileRotation`），其余装配结果照用，从头完整跑一遍。编译不过、运行报错（连段中断、等超时、超过帧数上限）的丢掉，按原因计数；写了"变奏"的切人没变奏（`introMissed`）的照常排名，另外标出来。
- **去重**：按指令序列（`rotationKey`）：同一角色相邻几行怎么断行不算不同的轴（Q 放在一行末尾与下一行开头是同一条）。
- **多轮**：`--rounds N` 时每轮从最好的 `--beam` 条（缺省 3）各再改一处（beam search），这一轮没有比最好的更好的就停；`--max-runs`（缺省 500）限制仿真次数。
- **输出**：排名、DPS 与变化、每轮时长、改法（"维里奈 Q：第 4 条第 5 个 → 第 8 条第 3 个（跳跃 之后、强化空中A1 之前）"，多轮时一步一段）；结果一样的（DPS 与每轮时长都相同，多半是同一处换个等价的位置）合成一行；最好那条改了的行。`--save 新.yaml` 把最好那条另存成场景（只换循环轴的条目行，其余连注释照原文），接着 `pnpm compare` 看差在哪。
- **例**（2026-10-20，只挪 Q）：
  - M0 代表轴：一轮 33 种、跑通 15 种（其余插进普攻连段中间、断了连段），维里奈的无归的谬误挪到她那一行开头 +1.64%（每轮 32.95 → 32.23 秒）；三轮（再挪散华、椿的 Q）+3.21%，161 次仿真、11 秒。
  - 视频轴 EQ 版：53 种、跑通 22 种，维里奈的无归的谬误挪到第二次上场（大招、跳跃之后）+0.55%：覆盖率不变（每轮 25 秒罩 20 秒），罩住的换成了散华的大招、椿的延奏；三轮（再挪椿的 Q 到 E2 前）+0.73%。
  - 心 · 雷主 · 卜灵（5 阶）：43 种、跑通 22 种，卜灵的无归的谬误挪到她第一行开头 +2.25%（雷主首位换成绝息魄的对照场景里 +2.21%），主要是每轮短 0.78 秒（原来放在震为雷之后，要等震为雷打完）；电磁效应的伤害在三人之间挪了位（卜灵 +566/秒、心 −298/秒），这部分受假设 `effect-owner` 影响。
- **网页**（v0.1.9，TD-12）："轴搜索"页，选项同命令行；结果每条能另存成场景（只换循环轴，改了的行注明"轴搜索改的"，`src/data/scenario-text.ts`）、一键去对比页和原轴比（时间轴对照）。跑不通的原因名 `FAILURE_LABEL` 在 `src/engine/search.ts`，命令行与网页共用。
- **以后**：从零排轴见 §6.2；排出来的轴可以再用这里的局部搜索微调。

### 6.2 套路卡与排轴（v0.1.9，设计，未实现）

§6.1 只会在一条现成的轴附近改一处，有三个限制：
- 跳不出原轴的打法框架。
- 不懂连段、冷却与协奏，一半以上的候选跑不通（视频轴 EQ 版 53 种只跑通 22 种）。
- 要两处一起改才变好的打法找不到。

玩家排轴也不是一个动作一个动作排的。玩家心里先有一个切入点（主 C 是谁、要吃上哪些 buff），每个角色再有几套基本固定的打法，比如椿盛绽一轮、散 ERZ、维 AAAEQ。排的是这几套的先后与谁切谁，几套之间的差别只在几个参数上，比如补几下 A、怎么入场。社区的排轴指南（NAMELAG，见开头"参考"）第 2 节就是这样做的：
- 每人一段"攒满协奏 → 延奏切出"；
- 辅助拆成两半，中间夹别人的动作；
- buff 都要罩住主 C 的爆发窗口；
- 中途临时切人时协奏不能已满，否则会误出延奏、丢掉后面的 buff。

所以这一节把"一套打法"当成封装好的单元（**套路**），先用仿真把每个套路量成一张**套路卡**，再在卡上排轴，最后用完整仿真定排名。这套做法借了别处现成的三种思路：
- **AI 规划的 HTN**：从切入点往下展开，只在给定的套路里排。
- **数据库的查询优化器**：一个套路的几种写法，按当时状态里要紧的那几样（前台、协奏满没满、椿在不在红椿……）排先后。相同状态只留最好的一条。
- **验证领域的反例引导精化**：在卡上算出来的，交给仿真核对；对不上的地方回写到卡上。

用途同 §6.1：检验与启发。排出来比原轴好的，是要拿实战核对的假设。

**① 套路**

一个套路是同一角色的一行轴：用现有写法，后缀照写（补位 `~` 也算），不含 `switch`。

套路有两个来源：
- **(a) 缺省**：从场景的循环轴和启动轴按行拆，写法一样的算同一个。
- **(b) 手写**：场景里另写 `search.routines`，可以是轴里没有的打法。这个字段要先加进 schema（TD-02）。

```yaml
search:
  routines:
    - 维里奈 A3-地面出场技 A4 A5 E                               # 维 AAAE：拆成两半的前一半
    - { line: 维里奈 Q 跳跃 强化空中A1 强化空中A2 强化空中A3, max: 1 }
```

`max` 是每轮最多用几次，缺省不限。辅助拆两半就写成两个套路，中间夹谁由排轴决定。

**② 套路卡**

每个套路用仿真单独跑几次量出来。每次的跑法：前面可以有一行铺垫（同一角色的上一个套路，给它要的前置状态），后面接一个"切走"或"接自己的下一招"，每种入场方式各跑一次。M0 和心队全部套路量一遍，是一两百次短仿真、几秒钟。

卡上记这些：

| 项 | 内容 | 例 |
|---|---|---|
| 入场方式 | 接着打 / 普通切入 / 变奏切入，下面各项按入场方式各记一份 | 维里奈 AAAEQ 要普通入场（地面出场技） |
| 前置 | 角色状态、资源门槛、要用的冷却 | 椿盛绽一轮要在盛绽状态；一日花要椿自己协奏满；维里奈两段带大招的不能挨着（冷却 25 秒） |
| 时长 | 两个：**到能切走**、**到能接自己的下一招** | 散华 ERZ 变奏入场 2.17 秒能切走；后面接自己的 A 要 3.60 秒 |
| 资源 | 名义协奏、名义能量（自己、分给队友的）；实际到账由排轴时的资源水平和上限决定 | 维里奈 R 跳 AAA 名义 66.85 协奏，视频轴里进这段时已满，只到账 28.73 |
| 伤害 | 只吃自己 buff 时的伤害，按乘区与标签分开记；队友的 buff 由排轴时乘上 | — |
| 给的 buff | 给谁、多久 | 维里奈延奏攻击 20 秒全队 |
| 异常效应 | 加几层、加几层爆发；消耗型的记它要多少层 | 雷主超负荷 +10 爆发；心照世·E 那段消耗爆发 |
| 结束状态 | 角色状态、有没有挂着后台动作 | 椿退出盛绽、进含苞 |
| 补位 | 补位 `~` 的套路是"攒到满为止"：记每下补位的时长、回多少资源、补到哪个阈值。时长 = 进来时的缺口的函数 | 雷主超负荷 Q 那行：进来时电涌已满只打 2–3 下（2.1–2.7 秒），从零开始要 14 下（10.9 秒） |

量卡用的就是现有仿真，引擎不用改。命令行 `pnpm cards 场景.yaml [--char 椿]` 出一张速查表，对人也有用。

**已实现（2026-10-21，`src/engine/cards.ts`、`src/cli/cards.ts`）**：
- 每个套路量 6 种上下文：入场（接着打 / 普通切入 / 变奏切入）× 出口（切走 / 接自己的下一招）。有铺垫的再量 6 种。另列原场景里每轮的这一段，以及它与"同入场方式的单独量"在时长上差多少。M0 视频轴 11 个套路、115 次短仿真，约 1.5 秒。
- **时长**：这段第一条指令开始，到下一条指令能开始。下一条自己在等冷却、资源、角色条件的时间（`exitWait`）不算，单独列出。切人冷却分两种情况：这段是切入的，切人冷却就是这次切入带来的，算这段的；这段是接着打的，切人冷却是之前的切人留下的，不算。
- **开局资源**：自己的大招能量 0；这段、铺垫或出口里有要能量的大招时，给到门槛（这一行标"自己的能量少算"）。协奏 0；变奏切入时，上一个人的协奏给到 100。
- **资源与伤害**：按"归到的动作"算，切走后在后台打完的也算。协奏、能量是实际到账，满了之后的不算，标出"满了"。还没记名义值，这是以后的事。
- **标记**：
  - `switchAtStart`：切走时大招才打了不到 10 帧（⑦ 的教训：多半是数据漏了切人锁）；
  - `needsSetup`：不铺垫跑不通，原因照写，如"要在盛绽状态下""一日花要协奏满"；
  - `teamMismatch`：队里某一轮与同入场方式的单独量差 ≥ 0.1 秒，多半在等冷却。M0 视频轴里维里奈 R 跳 AAA 在等她 25 秒的大招冷却。
- **还没做**：
  - 补位按缺口的函数化：现在只是如实量出跳过了几下；
  - 名义协奏和能量；
  - 只吃自己 buff 的伤害；
  - 两层铺垫：心照世相的几段、椿 REEZQ 的一日花要协奏满，一层铺垫不够，只能看队里的数。

**③ 验证（2026-10-21，M0 视频轴 EQ 版、心 · 雷主 · 卜灵 5 阶修复轴）**

验证的问题是：卡上的数，在队里和单独量的时候一样不一样。脚本是临时写的，结论如下：

- **时长**：入场方式、铺垫和出口（切走 / 接自己）都相同时，队里与单独量的一致，大多差 0 秒。
  - M0 的例子：散华 ERZ 2.17 / 2.17、椿盛绽一轮 5.48 / 5.48、维里奈 AAAEQ 3.07 / 3.07、椿 AE 1.00 / 1.00；
  - 心队的例子：雷主 E 1.20 / 1.20、卜灵雷山小过震为雷 QR 3.47 / 3.47、卜灵下落 AAEA 2.10 / 1.92。
  - 变奏入场多出来的时间每人固定：椿 +1.30 秒、散华 +1.05、卜灵 +1.23、心 +1.1、维里奈约 +0.9。
  - 对不上的都是在等别的东西：视频轴维里奈 R 跳 AAA 在队里多等 0.70 秒大招冷却，说明这条轴每轮的长度卡在她 25 秒的大招冷却上。
- **资源**：协奏、能量的名义值在同一种入场方式下一致，变奏入场固定多给一份。实际到账受上限影响：维里奈 R 跳 AAA 每轮浪费约 38 点协奏，散华 EQ 浪费约 16 点。卡记名义值，到账由排轴时按资源水平算，浪费也就顺带算出来了。
- **补位是参数**：同一行带补位的，时长随进来时的缺口变。
  - 心万阙垂天前那行，第 1–4 轮是 6.37、6.37、7.00、9.70 秒（8、8、9、10 个动作）。能量缺口逐轮变大，轴并不严格周期。
  - 心的共鸣效率换到 141.2% 的对照场景里，这一行一下都不补，每轮完全一样。
  - 所以排轴要带着资源水平跨轮往下算，不能假设每轮一样。
- **异常效应是跨人的生产者 / 消费者**：
  - 稳态里几乎每段开始时，敌人身上已有 10 层电磁效应，再加层全被上限吃掉；有用的只是电磁爆发：雷主超负荷 +10、卜灵 +6、心 +5–7。
  - 心照世·E 那段每轮 46–49 万伤害里，约一半是消耗爆发打出的效应伤害。
  - 所以卡要记"产出几层爆发"与"消耗几层"，排轴时像 buff 一样配对。
  - 定时结算的伤害落在哪一段看相位，每次几千到一万，按全队的每秒量算，不归到套路。
- **伤害不能当常数**：同一套路队里和单独差 1.3–2.5 倍（延奏、维里奈攻击、散华 6 链这些队友 buff），同一套路在不同状态下也不同（椿 AAAAA：普通 57k、含苞 118k）。所以卡记只吃自己 buff 的伤害，状态写进前置。
- **出口的差别有时很大**：量的时候心转相接切走 4.58 秒、接自己照世·E 5.87 秒；雷主大招接切走 1.20 秒、接自己 A 5.00 秒。这两处的"切走"太早，是构建漏读了"无敌期间不能切人"（⑦），修了以后切走要等到大招第 255 / 225 帧；两种出口仍可能不同（散华 ERZ 切走 2.17 秒、接自己的 A 3.60 秒）。

结论：封装成立。每个套路要记的上下文只有入场方式、自己的两三个状态、冷却、资源水平和敌人的效应层数；跨人的依赖只有 buff 和异常效应两类，都能写成"产出 / 消耗"。

**④ 排轴：在卡上排，用仿真定**

- **切入点**：参考轴（缺省），或者手写一个"意图"：主 C 是谁、谁速切、哪些 buff 要罩住主 C 的爆发。排轴只在给定的套路里展开。
- **在卡上排**（毫秒级，不跑仿真）：
  - 状态 = 前台、各人协奏 / 能量、冷却、各人的角色状态、敌人效应层数与爆发、各 buff 还剩多久。
  - 转移：
    - 按卡算：时长取出口对应的那个，资源按名义值加、受上限截，buff 和爆发按产出 / 消耗配对。
    - 相邻两个套路的角色不同，中间插 `switch <后者>`；切出者协奏满了就写成 `switch X 变奏`，与游戏一致（TD-09 §3.5）。
  - 搜索：beam search 或动态规划，相同状态键只留最好的一条（查询优化器的做法）。
  - 先放主 C 的爆发，再倒着补它依赖的 buff 和爆发层数；buff 尽量晚放，让持续时间罩住窗口（构建系统"按依赖倒推"的做法）。
  - 剪枝：
    - 前置不满足的丢掉。
    - 入场方式不合的丢掉：要普通入场但切出者协奏已满（会变奏），或者要变奏但协奏没满。这就是指南里"中途临时切人时协奏别满"那条。
    - 一轮长度下界：每个要用的冷却，一轮至少一次，所以每轮至少和最长那个冷却一样长。前缀已经超过"下界 + 余量"还接不回去的丢掉。
  - 循环：一轮排完要能接回开头；资源水平跨轮往下算，补位的套路按每轮实际的缺口算时长。
  - 卡上的分 = 每个套路自己的伤害 × 当时罩着的队友 buff + 消耗爆发的效应伤害，除以时长。它只决定留谁，不影响最后的数。
- **用仿真定**：
  - 卡上最好的几十条写成循环轴，启动轴照原场景，完整跑 `repeat` 轮（缺省 4），按比较口径（§3）排名。这和 §6.1、`pnpm compare` 是同一口径，所以最后的数与仿真一致。
  - 第 2 轮起跑不通的丢掉。
- **回写**：仿真与卡上预测差得多的（某段实际长了、某个 buff 没罩住），把差别记成这张卡在这个上下文里的修正，再排一遍，通常两三轮就稳了。
- **输出**：
  - 同 §6.1：排名、DPS 与变化、每轮时长、计划（套路名 → 套路名，切人标出普通 / 变奏）、`--save` 另存。
  - 另外列出每轮浪费的协奏和能量，以及 buff 有没有罩住主 C。
  - 最好的几条可以再用 §6.1 微调（`--polish`）。
  - 命令行 `pnpm plan 场景.yaml`；网页并进"轴搜索"页。

**⑤ 引擎**

量卡和最后的完整仿真都只用现有接口。总设计 §3.7 要求的"状态拷贝、从中间接着跑"，这一版用不上；等卡上的模型不够准、要在仿真里展开时再做。要做时，闭包里的事件总线、`lastBattle`、`warned`、钩子上下文要挪进状态或在拷贝时重建，且只在总线排空时分叉。

**⑥ 先后**

**⑦ 待确认**

- **大招的切人锁（2026-10-21 已修）**：量卡时发现心的转相、万阙垂天，雷主的大招在仿真里第 0 帧就能切走。查 xlsx：三个大招的备注都是"无敌期间不能切人"（不带帧数），帧数在「无敌启动帧 / 无敌持续帧」两列，构建没读。
  - 现在构建抽出这两列，"无敌期间不能切人"的切人锁 = 无敌结束（谐度破坏仍按整个动作）；转相的无敌持续帧是空的，按同组全局时停 254 帧推断，写在心的模块里。同一处还补上了心、雷主的变奏、强化E、强化重击等 16 个动作的锁，M0 三人不变（xin-confirm Y18）。
