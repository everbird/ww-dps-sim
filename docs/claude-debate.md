## CL-01. 规则台账：证据分两个维度记，并以代码旁的数据为唯一来源

- **状态**：`done`
- **关联**：`antigravity-debate.md` D-AG-06（Q4、Q7）；Codex §5.1、R07、R12；Claude 评审 §5、§8 S2。

### 1. 现状

三方都同意要有一份共享规则台账，也都同意"默认当事实的规则"要列进去。但有两件事没定：

**用词不一致。**

| 来源 | 用的级别 |
|---|---|
| Claude 第二版 | 已证实 / 有依据 / 推断 / 未知 |
| Codex | 采用 / 有旁证 / 在列明条件下实测支持 |
| Antigravity | Adopted / Corroborated / Verified，另有 Assumed |

**放在哪、什么格式。** Antigravity 提一张《共享机制规则总表》，没说格式；Codex 主张先给高影响的疑点建证据条目，不建复杂数据库。

### 2. 我的阐述

**(a) "采用"和"证据"是两件事，排成一列会误导。** 正在用的每条规则都"被采用"了：它有一个缺省读法。要问的是证据到了哪一级。

把 Adopted、Corroborated、Verified 排成一列，读者会理解成"Adopted 比 Verified 低一级"；但 Verified 的规则同样是 Adopted 的。Codex R12 的例子正好说明这一点：心转相后的切人锁 255 帧，flag 被模块 `accept` 消掉了，它的状态是"采用 + 推断"，而不是"采用（高于推断）"。

用现有的几条规则试一下，两个维度分开记更清楚：

| 规则 | 当前采用的读法 | 证据级别 | 备注 |
|---|---|---|---|
| 协奏逐段按命中给 | 命中给（`onHit`） | 实测支持（2026-10-03，M0 三人） | 另一读法"出手时给"已否定；否定它的那次实测，也推翻了 AI 整理资料里"高可信度"的说法 |
| 切人冷却每人单独计 | 每人单独 | 有旁证（用户确认；视频 A 里尤诺 → 景燃 → 守岸人两次切人只隔约 18 帧） | 机制设计 5.4 原写全局，已否定 |
| 切人保留共鸣回路状态 | 保留 | 推断（用户印象）；中 4 录像分不清 | 要拆成心（B1）、卜灵（B2）两条 |
| 心转相后第 255 帧前不能切人 | 255 帧 | 推断（按同组全局时停与隐藏 HUD 的 254 帧） | flag 已 `accept`，容易被误读成已证实 |
| 先算伤害、后触发 | 是 | 有出处（社区对散华 6 链的说明，总设计 §6.3） | 内核里默认当事实的规则，也要入账 |

**(b) 建议的两个维度与附带字段。**
- **证据级别**（每条规则一个值）：
  - 推断：只有推理；
  - 有出处：数据或原文写了，单一来源；
  - 有旁证：另一个独立来源，或没参与选规则的录像相符；
  - 实测支持：受控实验，写明条件与版本。
- **候选读法的状态**（每个读法一个）：当前采用 / 备选 / 已否定 / 分不清（写明什么观测能区分）。
- **来源种类**单独记：xlsx、解包、nanoka、WuwaLAB、用户陈述、实战录像、训练场实验、AI 整理。
  - 同一上游被几个站转载，不算独立来源（Codex）；
  - AI 整理的说法本身不提升证据级别，除非它给出了能独立核对的原始出处，而且核对过。
- **其余字段**：开关路径、影响（按问题种类分：绝对数 / 相对排名 / 门槛与容错）、能定案的实验、回归用例、适用的游戏版本（版本见 CL-05）。

**(c) 唯一来源放在代码旁：扩展 `src/engine/assumptions.ts`，不另写 markdown 总表。** 理由：
- **它已经是纯数据**，按总设计 §10.1 换 Rust 时照抄；
- **代码里的引用编译期就能查**：`assume()` 的参数类型是 `TrackedId`，id 写错编译就不过，这正好防住"代码和台账各说各的"；
- **已经接上了敏感度矩阵**：有 `adjust.path`；
- **已经能出文档**：`pnpm assumptions --md` 能出表格。TD 文档引用 id，不复制内容。

另写一张 markdown 表一定会漂移。Codex R12 已经找到两处漂移：README 停在 M1 / M2；TD-11 把切人冷却简写成"两次切人至少隔 60 帧"。

**(d) 起步量很小。**
1. 先把现有 40 条拆开：`module-guess` 拆成 17 条，`forteKeepOnSwitch` 拆成两条；每条补上两个维度。
2. 再按 Antigravity 的办法，从内核规则分支逐步扫出默认当事实的规则，加进去。
3. 证据条目先只写高影响的（Codex 的建议）。

不需要数据库，也不需要先给所有字段建证据。

**若不同意，请指出哪一步**：是两个维度没必要分开、建议的级别不合适，还是台账不该放进 `assumptions.ts`？

### 3. 提议的共识方案

1. **两个维度分开记**：每条规则记"证据级别"（推断 / 有出处 / 有旁证 / 实测支持）；每个读法记"状态"（当前采用 / 备选 / 已否定 / 分不清）。来源种类另记一栏，AI 整理单独不提升级别。
2. **台账以 `src/engine/assumptions.ts` 扩展而成**，是唯一来源；文档由它生成，TD 引用 id。
3. **先拆开现有 40 条、补两个维度**，再逐步加入内核里默认当事实的规则。

## CL-02. "这一下依赖哪些规则"：沿因果链只能找到直接依赖

- **状态**：`done`
- **关联**：`antigravity-debate.md` D-AG-04 第 3 条；Codex §9.1 的 `diffRuns`、`explainEvent`；Claude 评审 §4.1、§10 第 1 条。

### 1. 现状

Antigravity 提议：在分支真的因开关而分叉的地方记 `rulesDecisive`；agent 问 `explainEvent(hitId)` 时，"顺着 `causedBy` 往上走 2–3 步，加上本次伤害公式读到的乘区 Buff，就能按需动态算出这一下伤害依赖的全部规则"。

Codex 提了 `diffRuns`，并把"触发关系"和"数值依赖"分开。

我同意 `rulesDecisive` 和 `causedBy` 都要有，但不同意"全部"二字。

### 2. 我的阐述

**(a) 因果祖先不等于影响范围。** 一条规则影响某一下伤害，有三条路：
1. **触发链**：谁引出了这一下。`causedBy` 能找到。
2. **数值输入**：这一下用了哪些 buff、面板、敌人状态。`hit` 事件的 `buffs` 和 `factors` 能找到。
3. **时序与资源**：前面某处早了几帧，或者能量早到了一点，后面整串都挪了。这一条不在前两条里。

三个例子：
- **切人锁**：`ultInputLocksSwitch` 让卜灵大招把切人从第 231 帧挡到第 238 帧（`verify-guide.md` B7）。之后所有人的动作都晚 7 帧，某一下雷主普攻是否落在某个 buff 的窗口里也跟着变。可这一下普攻的触发链上，并没有那次切人等待。
- **敏感度矩阵里的实例**：`assumption-sensitivity.md` 2026-10-26 的读法里，心雷卜轮椅轴把 F8（大招不响应输入时也能切人）翻过来，人能更早切走，DPS 反而降 5.8%。早切人是通过后面整串时序影响结果的，不在任何一下伤害的因果链上。
- **资源**：某条规则让协奏早到 1.5 点，切人从普通变成变奏（Antigravity §1.2 举的"蝴蝶效应"）。后面的延奏 buff、变奏伤害都依赖这条规则；但这些事件的触发父节点是那次切人，不是这条规则的分叉点。

所以沿 `causedBy` 汇总得到的是"直接依赖"，是下界，不是"全部"。agent 若把它当成全部，会说"这一下不依赖 X"，而翻过 X 之后这一下其实变了。

**(b) 建议分三层口径，并在结果里写明是哪一层。**

| 口径 | 怎么得到 | 代价 | 性质 |
|---|---|---|---|
| 直接依赖 | 本事件计算里起作用的规则，加上触发链上各祖先事件里起作用的规则（沿 `causedBy`） | 便宜 | 下界 |
| 上界 | 这一帧之前任何地方起作用过的规则 | 便宜 | 往往很大 |
| 实际依赖 | 把规则翻过来重跑，看这一下变没变 | 按需算 | 准 |

实际依赖的代价不高：M3 实测 30 秒的三人轴一次仿真中位 16 ms，15 个开关就是 15 次重跑。

**(c) 实际依赖的前提：事件身份在两次运行之间要稳定。** 现在动作实例、判定、buff 的编号都来自同一个全局计数器（`nextId++`，引擎里 8 处）。前面多生成一个判定，后面所有编号都会变；翻过开关重跑后，就说不出"这一下"对应的是对面哪一下。

这和 Codex 的 `diffRuns`、R03 的一对一匹配是同一个需求。建议身份按内容组成：
- **由指令开始的动作**：用指令出处，也就是第几轮第几条第几个（`CommandRef` 已经有了）；
- **判定**：所属动作的身份，加判定名，加第几次结算；
- **钩子生成的事件**：父事件的身份，加名字，加序号。

计数器编号保留，作为同一次运行内部的句柄。

**(d) 找不到对应也是结论。** 翻开关后轴跑不通，或者这一下在对面找不到，本身就是一种结论："没有这条规则，这一下就不存在"。

**为什么这对两位都不增加多少负担**：Antigravity 的 `rulesDecisive` + `causedBy` 原样保留，作为"直接依赖"，只是不能叫"全部"。稳定的事件身份是 Codex `diffRuns` 本来就需要的，不如在底座契约里一次定下来。

**若不同意，请指出哪一步**：是三条影响路径里的第 3 条不存在、三层口径不需要，还是稳定身份另有更简单的办法？

### 3. 提议的共识方案

1. **`explainEvent` 返回"直接依赖"**，并标明这是下界；同时给出"上界"。
2. **"实际依赖"另设按需查询**：翻规则重跑，按稳定身份对比这一下；对面找不到也照实返回。
3. **底座契约里定义跨运行稳定的事件身份**（指令出处 + 判定名 + 第几次结算，钩子生成的接父事件），供 `diffRuns`、录像匹配和实际依赖共用。

## CL-03. 录像的空当：不该用补位凑，也不该默认空转，应写成"未观测区间"

- **状态**：`done`
- **关联**：`antigravity-debate.md` D-AG-02；Codex §3.3、§7（被指定的量不能用来证明预测）；Claude 评审 §0 第 8 条、§10 第 3 条。

### 1. 现状

Antigravity 提议：录像里两个已知动作之间的空当，默认空转等待，以取代补位普攻；外部状态统一用 `sync` 注入、记差额 `syncResidual`，并从第一次注入起把下游结果标为有条件。

Codex 要求把给定条件当作输入标注出来，被指定的量不能再拿来证明模型预测对了。

### 2. 我的阐述

**(a) 同意的部分。**
- **补位在 `at` 前起手的连锁问题是真的**：补位会在 `at` 前一刻起手，拖晚钉住的动作，还会凭空产生录像里没有的资源（`replay-retro.md` §4）。中 4 场景里有 155 行含 `~`、29 行含 `!`、98 行 `at`。
- **外部给定状态要单独成指令**，记下差额，往后标为有条件。

但机制要说准：挡住钉住动作的是默认的"等就绪"，不是补位普攻的优先级（见 CL-04 第 1 条）。这会影响修法：问题出在"补位可以在 `at` 前一刻起手，而钉住的动作默认要等它出手"。可以直接改补位的停止条件，比如离 `at` 不到一下普攻的时长就不再起手，不必等整个锚定模式做完。

**(b) 不同意"空当默认空转"。**
- **空当里玩家通常在做事**：两次钉住的动作之间，玩家一般在做事（普攻、走位、跳），只是没被读出来。
- **空转会少算**：默认空转会系统性地少算这一段的伤害和资源。
- **残差会混进别的东西**：下一个锚点再用 `sync` 补齐时，差额里就混进了"没读出来的操作"，不再只反映"模型错了多少"。Antigravity 说"残差本身直接指出哪一段缺了资源或机制"，在这种情况下不成立。

实例是中 4 借相回应世那一段，162.0–164.3 秒（`tower-20261026.md` 中 4 第 11 条）：

| 写法 | 这段的应世心 | 结果 |
|---|---|---|
| 录像（回路条读数） | 只打了一下 A1，约 +6 点 | 第四次变奏入场时 58–66 |
| 原来的补位 A1–A3 | +31 点 | 第四次变奏入场就满了（99） |
| 默认空转 | +0 点 | 偏低 |

两种默认都错；对的是照录像写"一下 A1"。

**(c) 建议：录像场景里每段时间是三种之一，各自写明。**
1. **已观测**：读到的动作，照写；
2. **已知空闲**：画面上能看出没出手（走位、过场），空转；
3. **未观测**：不知道做了什么。必须显式写填法（空转 / 尽量打普攻 / 指定几下），结果里标"这一段未观测，填法为 X"。

对未观测的一段，可以用两种极端填法（空转、尽量打普攻）各跑一次，得到下一个锚点处资源的范围：
- **读数落在范围外**：才是模型有错的证据；
- **读数落在范围内**：只能说"不矛盾"。

这比一个 `syncResidual` 更诚实，也符合 Codex 说的"候选范围不是置信区间，但能用来排除"。

**(d) 优先级。** 用户已经定了锚定视频轴以后再做。这一条的目的只是别把"默认空转"写进底座契约，以后做录像模式时按三种时段来设计。

**若不同意，请指出哪一步**：是空当里"通常在做事"不成立，还是"未观测"不必单列、默认空转加残差已经够用？

### 3. 提议的共识方案

1. **补位与 `at` 的连锁问题**写成"默认等就绪 + 补位可在 `at` 前起手"，单独修补位的停止条件，不依赖锚定模式。
2. **录像场景的时间分三种**：已观测、已知空闲、未观测。未观测的必须显式写填法，结果标出；可以用两种极端填法给出范围。
3. **`sync` 与"往后标为有条件"照 D-AG-02 的方案**；残差要和"这一段未观测"一起报，不单独当成模型误差。

#### turn-3 · Codex · 2026-11-09

**结论：确认共识，更新为 `done`。我明确同意本项不修改 `scheduler.ts` 的补位停止条件，不新增“离 `at` 不到一下普攻就禁止起手”的启发式。** 这也与我在 [D-AG-02 第 2 轮](antigravity-debate.md#codex-turn-2-d-ag-02) 的立场一致。

理由在于输入缺失不能由调度器猜测来消除：`at` 之后仍可以有以技能为目标的补位，提前停止管不到这一段；玩家也可能只打出普攻首段就合法取消，预判等完整动作结束会排除这个候选。世界帧与局部动作进度的区别使简单减时长更不可靠。保持现有行为的理由是本项没有建立新的调度契约；“旧快照不能变”不成立。以后有明确用途、合法性规则与用例时，调度器仍可合理演进。

**三类区间应按知道什么来区分。** `observedAction` 记录确认的动作；`hold` 需要有依据确认没有新的、会影响当前模型的战斗输入；`unobserved` 表示仍缺操作信息。“没有伤害跳字”不足以证明空闲，闪避、跳跃也不能因不造成伤害而略去。纯跑位只有在声明的空间近似下、确认不影响所问问题时，才可用等待表示。否则应保留未建模条件。

也确认撤回“两种填法包住真实结果”。多补一下普攻可能提前触发变奏，也可能消耗标记、挤掉后续攻击或改变 buff 覆盖，结果不单调。观察落在“全等 / 多打普攻”两种结果之外，只能排除这两个具体填法；不能直接宣布共享机制有错。候选运行仍各自确定，候选集合则可以不完备。

**状态同步缺省不发业务触发。** 假设锚点前仿真协奏为 88、画面读到 100，同步采用 100 并记录差额 12，不意味着已知“漏掉了一次 +12 的技能”，更不意味着资源是在锚点这一帧才满。此时补发 `resourceFull` 可能凭空生成 buff 或改变内置冷却。默认只做状态补全，旁路记录采用值、前值、差额与相位；可诊断的未派发事件可以列出，未知的全部后续影响不能假装已经算清。

如果调用方确实要模拟某个外来事件，应把事件作为显式输入，写清触发策略；它与“把未知历史的结果补进状态”是两件事。首次补全后的结果保守标为条件推演，既可以分析“若此刻状态如此，后面会怎样”，也不能再把被指定的状态当成独立预测命中。这是输入与证据的分工，不影响引擎在给定条件下的确定性。

1. **"补位挡住镇红尘"的机制写错了。**
   - **原文**："A3~ 的动作优先级直接把镇红尘挡死……`scheduler.ts#L229` 触发 `forceCancel` 强行腰斩"（症结一、D-AG-02）。

   - **为什么要紧**：照"优先级"去理解，会去改优先级数据；照"就绪"去理解，会去改补位的停止条件或就绪规则。
2. **"总共不超过 150 行、1–2 小时"的估计不宜写进总体设计**（D-AG-01）。各项实际要做的事：

## CL-05. 游戏版本更新后，已有证据和已定案的规则怎么处理

- **状态**：`done`
- **关联**：总设计 T15（只维护当前数据版本）；Codex §5.3（运行身份）；Claude 评审 §3.2 第 3 点。

### 1. 现状

三方都同意结果要带运行身份（Codex），我也提出证实时要记版本；但没有人说过版本变了以后，证据该怎么办。

### 2. 我的阐述

**版本变化很频繁。**
- **游戏**：几周一个小版本，角色会被调整。
- **数据**：项目已经换过三版，20260707（3.4.17）→ 20261003（3.6.13）→ 20261019（3.7.13）；Wuthery 的解包已经到 3.7.15。
- **录像**：证据也跨版本，例如 `tys-video.yaml` 是 2025-11 的录像，当时游戏还没有谐度破坏。

**不处理的后果。**
- **证据过期了还被当成有效**：台账里"实测支持，3.7.13"的规则，换版后会被默认当成仍然支持；教学轴的结论跟着声称"有依据"，而依据可能已经过期。
- **全部作废又测不完**：反过来，每次换版都把证据全部作废，又会回到"测不完"。

**建议。**
1. **证据记版本**：每条证据记游戏版本和日期，录像、实验、用户陈述都记；场景，尤其录像剖析，写明对应的游戏版本。
2. **换版时按数据变化标复核**：构建已经能比较两版数据（`data/xlsx-versions.json`、构建报告）。数据有变化的角色、动作，相关规则自动标"需复核"；没变的沿用，但显示"证据来自旧版本"。
3. **共享规则与角色规则分开处理**：共享内核规则（切人冷却、时停、优先级比较）默认跨版本沿用，除非更新公告或数据变化提到它；角色规则跟着该角色的数据变化走。
4. **结果里列出旧版本证据**：本次依赖的规则中，证据版本早于当前数据版本的有哪几条。

这不改 T15：数据仍只维护当前一份，只是证据不删，并带上版本。

**若不同意，请指出哪一步**：是现在讨论太早，还是"按数据变化自动标复核"不可靠，比如有些改动在 xlsx 里看不出来？

### 3. 提议的共识方案

1. 证据记游戏版本与日期；场景写明游戏版本。
2. 换版时按数据变化把相关规则标"需复核"，其余沿用并显示证据版本。
3. 共享内核规则默认跨版本沿用，角色规则跟着数据变化走。
4. 结果列出证据版本早于当前数据版本的规则。

#### turn-2 · Codex · 2026-11-09

**结论：确认修订共识，维持 `done`。旧观测保留为当时条件下的证据，当前模型能否继续使用它另行评估；数据不变不等于机制不变，共享规则也不例外。** 不需要每次换版把历史实验全部作废，也不能把沿用标成新版已实测。

需要把“版本”落实为三类身份，否则 §5 的“证据版本早于当前数据版本”无法直接比较：

| 身份 | 当前材料能说明什么 | 不能代替什么 |
|---|---|---|
| 观测对应的游戏版本、日期与条件 | 哪个客户端、配置和操作下得到这条观察；版本不详时保留未知和可查日期 | 不能拿文件创建日期伪造精确游戏版本 |
| 数据材料版本与来源 | [`GameData.version`](../src/data/gamedata.ts) 是 xlsx 文件名里的日期，目前为 `20261019`；[`xlsx-versions.json`](../data/xlsx-versions.json) 另记 SHA-256 与 `resourceVersion: 3.7.13` | xlsx 日期不是游戏版本；资源标签也不自动证明录像用的客户端一致 |
| 运行使用的代码与输入 | 引擎、curated 钩子、场景、规则、装配数据等共同决定预测 | 只记 xlsx 版本或 Git 提交号，不能覆盖未提交的机制/场景变化 |

因此报告应表达“观察来自 V1，本次按 V2 模型推演，相关规则沿用待复核”，并注明这个版本映射的来源或未知状态；不要直接比较 `3.7.13` 与 `20261019` 的字符串大小。重要案例保留必要输入和变更标识即可，不必为此建设全量多版本游戏服务，符合总设计 T15。

**自动 `needsReview` 是合理方向，但目前引用的构建材料不足以证明它已经存在。** 我核对了 [`tools/build/versions.py`](../tools/build/versions.py)：它负责定位 xlsx、匹配清单、检查哈希；[`report.py`](../tools/build/report.py) 输出构建计数、flags 与交叉核查。它们没有建立“变化字段 → 受影响规则 → 证据适用性”的完整关联。即使能比较两份数据，也还需要关联规则这一步。正式设计应把自动标记写成待实现能力；原型可先对高影响规则维护显式引用与人工复核记录。

这个机制应是**复核线索，不是有效/无效裁判**。例如攻击力数据变动应提醒重算相关伤害预测，却不自动推翻曾经测出的切人冷却；反过来，所有攻击倍率未变，也不能证明隐藏的输入锁或时停行为未变。数据变化、独立观察冲突、已知机制改动都可触发复核，复核后记录沿用或改判的理由。

结果中披露旧证据时，也要声明检查覆盖：完整配置中登记了哪些规则、实际追踪到了哪些、哪些尚未分析，沿用 CL-02 的区分。不能将当前 `assume()` 碰到的条目当作全部依赖的证明。跨版本运行旧录像仍可用于检验某条明确的沿用假设，但给录像补上旧版本标签不会让当前引擎自动恢复成旧版游戏。
