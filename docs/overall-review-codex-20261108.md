## 1. 用户目标与本轮方向调整

最初的问题是：希望用逐帧仿真分析教学轴，或结合深塔、矩阵、全息视频，理解某些时间点的具体状态；现有原型陷入需要大量实测校准的困境。

在首个应用的选择上，用户明确选择了“读懂教学轴，并解释每个操作的必要性和容错”。据此形成了 [教学轴解释提案](rotation-explanation-plan.md)。随后用户进一步澄清：

- 逐帧仿真引擎是底座，教学轴、实战分析和 AI agent 都是使用者。
- 优先把底座做好，依靠应用提供真实场景来验证底座。
- 希望像编译器一样，把轴与配置转换成有时间顺序的事件和状态，支持定量、确定性的分析。
- 困难包括第三方或解包数据并非绝对可信，以及数值不符时缺少成熟的定位和收敛机制。

因此形成了 [底座路线提案](engine-foundation-roadmap.md)。用户认可这次方向，并要求先讲透运行时、验证方法、证据链与不确定性的管理，暂不急于实现。

本轮应保留的优先级是：**以可复用、可查询、可诊断的逐帧仿真底座为建设重点；教学轴作为优先验证应用。** 早期“先交付教学报告”的建议保留为应用设计，不再主导底座建设顺序。

这里区分三种状态，避免把讨论写成已经实施的决定：

| 状态 | 本轮内容 |
|---|---|
| 用户已明确的方向 | 底座优先；应用提供验证场景；重视确定性、数据依据和差异收敛；先理清思路 |
| review 已确认的事实 | 校准时钟说明相互冲突；出处推导存在代码注明的局限；另有已复现的实例、统计边界和比较状态问题，见 §4 |
| Codex 提出的设计建议 | 状态查询边界、事件直接原因、观测 schema、诊断流程、候选机制管理、P0–P4 路线；尚未逐项实施或确认为正式规格 |

## 2. 底座要作出的承诺

建议目标是：给定明确的数据、机制、配置、初态与操作策略，确定性地执行战斗过程；允许查询状态及事件的来由；与游戏证据不符时，能够复现问题、定位有证据的差异、排除候选原因，并说明剩余的不确定性。

“确定性”描述同样输入能否得到同样结果。“符合游戏”描述所选模型能否解释或预测游戏中的现象。两者需要分别建立。

逐帧推进表示计算的时间粒度，不自动意味着每个真实游戏时点已经测准到一帧。底座质量可以先在一个小的机制集合上做完整，再扩大覆盖。

采纳 Claude §2 的范围划分：**执行器、共享机制、角色内容、分析应用分别管理**。不把“所有角色都校准完”当作底座完成条件；也不把放在 `src/engine/` 里的所有文件都算作执行内核。搜索、择优、录像贴合和矩阵计分是消费者。边界应先由依赖和接口体现，搬目录可以随后做。角色钩子的调用顺序、状态存放与查询契约仍属于底座，必须用少量有代表性的角色组合验证，不能因“内容另算”而排除这条集成路径。

### 2.1 为什么区分三个问题

这是针对本项目选用的工作分法：三个问题可以独立出错，处理方法也不同；并非 NASA 规定必须恰好分成三层。

| 问题 | 例子 | 需要的工作 |
|---|---|---|
| 实现是否符合规格 | 规格要求 E 命中加 10 协奏，程序却结算两次 | 查执行过程、修程序、增加对应边界用例 |
| 模型是否符合游戏 | 规格要求命中时加协奏，游戏实际在起手时加 | 设计能区分时机的观察，修改规则解释 |
| 本次分析是否适用 | 代码和模型都正确，但场景与录像使用的武器、初态或环境不同 | 修输入或说明适用范围，重新进行可比的分析 |

不能仅通过最终数值接近判断这三项都成立。例如，程序错误地结算两次资源，再把数据从 10 改成 5，也会得到累计增加 10 的结果。录像暂时对齐，但程序错误被写进了模型参数，换一个触发路径就可能再次失配。

实现检查支持“程序在已检查条件下按约定工作”；游戏观测支持“约定在这些游戏条件下成立”。单元测试、不变量、golden 和 conformance 都有价值，但不能互相替代，也不能单独证明现实模型正确。由同一资料驱动的实现与参照一致，无法同时证明上游资料没有错误。

### 2.2 NASA 的方法可借鉴什么

NASA 的说明区分 verification（符合要求与规格）和 validation（从预期用途出发，评估模型对现实的准确表达），并强调预期用途与允许用途的明确性。[NASA 模型与仿真 FAQ](https://public.ksc.nasa.gov/mns/faq/)

本项目可以据此采用以下做法，规模保持适合个人原型：

- 为要回答的问题选择检查对象。解释提前切人的容错，要检查资源到账、输入锁、取消窗口；总 DPS 接近仍不足以支持这些结论。
- 每项规则记录已支持的条件。一次单独命中对齐，不自动覆盖 buff 刷新、后台触发和取消后的行为。
- 给结果附上适用范围和有关假设。用具体的验证覆盖情况代替整个引擎的单一“准确率”。
- 先检查比较工具和执行实现中可独立验证的部分，再把剩余疑问交给游戏实验，减少无效实测。

这些是对项目的建议，不要求引入航空航天项目的审批、组织流程或重型质量体系。当前原型可以边建设边补证据，不需要等全部机制验证完成才产生价值。

## 3. “明确运行时”具体指什么

这里的运行时指正在执行的模拟战斗及其推进规则。现有 `kernel`、`scheduler`、资源和触发模块已经承担这些职责；建议是把行为契约和可观察能力明确下来。

### 3.1 编译、执行与事件流

```text
轴、配置、所选数据和机制
          ↓
解析与装配：动作定义、指令、条件、初态、策略
          ↓
运行时：调度 → 推进动作 → 命中与资源 → 触发 → 计时
          ↓
有明确顺序的事件 + 状态查询 + 执行诊断
          ↓
教学轴分析 / 实战对照 / AI agent / 其他应用
```

编译器的类比可以延伸为“编译器＋执行器＋调试器”。编译阶段理解轴和动作，运行阶段根据资源、冷却、取消、时停与触发结果决定实际发生时刻。全部输入固定后，可以一次性生成整个事件流；这个生成过程本身包含仿真执行，不能只拼接固定动作时长。

建议的抽象契约为：

```text
(S[f + 1], E[f]) = step(S[f], Program, Model, Environment, Policy)
```

这是概念表达，不是新增的已实现 API。`S[f]` 包含该边界的完整执行状态和调度位置；`E[f]` 保留这一帧中的实际顺序。抽样时 RNG 状态属于执行状态；默认期望值模式继续遵守总设计 T4。

### 3.2 同一帧也有先后

以下是人造例子，数值不代表某个角色的实测规则；“等满协奏再切”是描述性策略，不是在提议新增条件分支 DSL。

甲第 0 帧施放 E，协奏为 90；E 第 30 帧命中并增加 10；策略要求满协奏后切乙；其他切人条件均满足。另设乙的变奏在局部第 20 帧触发甲的延奏，没有时间膨胀和其他资源变化。采用当前内核 P2 检查指令、P4 结算命中的顺序：

| 边界 | 甲的协奏 | 解释 |
|---|---:|---|
| 第 30 帧开始 | 90 | 本帧命中尚未结算 |
| 第 30 帧检查指令 | 90 | 满协奏条件未满足 |
| 第 30 帧命中之后 | 100 | 命中增加 10 |
| 第 31 帧开始 | 100 | 下一次检查能看到新资源 |
| 第 31 帧切人之后 | 100 | 乙开始变奏；甲的协奏尚未清零 |
| 第 51 帧延奏触发之前 | 100 | 乙的变奏走到局部第 20 帧 |
| 第 51 帧延奏触发之后 | 0 | 此时清零甲的协奏并处理延奏效果 |

**更正原文**：先前把“切人之后”直接写成 0，不符合当前 TD-05 §4.2 和 `switch.ts`。切人、入场变奏、离场角色的延奏以及协奏清零必须分别讨论。现有真实数据用例也能直接看到：散华满协奏切椿，切人在世界第 0 帧，散华协奏在第 36 帧的延奏触发时才清零（`tests/td05.test.ts` T05-2；本轮重新运行确认）。

因此，“第 30 帧是多少”需要指定边界。建议 `stateAt(f)` 统一表示世界帧 f 开始、P1 前的状态；事件前后查询明确指向事件实例。帧内实际顺序也应保存，不能只按帧号排序后随意处理并列项。

开局常驻 buff、`onResolve` 与相应事件处理属于初始化；建议 `S[0]` 指初始化完成后的首个 tick 起点，初始化事件单独标记。事件区间使用明确的 `[from, to)`。

上述例子说明执行约定的后果。游戏是否采用同样的边界顺序，仍属于现实验证的问题。

### 3.3 游戏限制、操作策略和指定条件

| 类型 | 例子 | 应用应如何解释 |
|---|---|---|
| 所选模型中的游戏限制 | 能量不足、冷却未好、输入锁未结束 | 当前条件下不能执行 |
| 调度策略 | 可以切，但等判定出手；自动谐破；有空补位；额外操作延迟 | 本次采用的操作方式选择了等待或插入 |
| 用户或录像给定条件 | `at` 对时、能量满、指定失谐 | 这是输入的一部分，应说明它限制了哪些预测 |

上表描述现有引擎可表达的输入，不是在要求每种应用都开放这些写法。`!` 仍按当前语义跳过等出手，不意味着绕过能量、输入锁等其他合法性检查。记录“等待 5 帧”时，应说明是哪一类原因，否则无法判断这段等待是否必要。

当前 `switch 乙 变奏` 也不是“无限等待直到协奏满”的硬断言：调度器会在协奏不足且前招尚未出手完时等待；其他条件允许后若仍不足，会普通切入并报告 `introMissed`。因此 §3.2 的描述性策略不能直接当作这条指令的完整语义。未来 `whyNot` 应明确返回的是首个检查到的阻挡，还是已检查的全部阻挡；当前调度器多处遇到第一项就返回。

**交叉阅读后的新增建议**：采纳 Claude §0、§1.5 与 Antigravity D-AG-06 的教学轴操作约定：首个教学轴入口要求明确动作，取消方式与谐度破坏由轴写出，禁用 `~`、`?` 与自动谐破。这样做的理由是忠实表达作者打法、减少引擎替作者选动作；这些策略在固定输入下本来也可以是确定的，不能把“不够明确”误称为随机。该约束属于应用入口，不需要删掉底座已有的通用调度能力。

我赞成保留有规格可查的按意图等待：变奏前等当前动作出手、空中入场等起跳、出场技等后台动作结束。输出应指出采用了哪条约定；若最后仍未达到轴要求的变奏等结果，严格教学轴应报告意图未满足，不能把普通切入当成成功完成。取消可以先写方式，由模型求最早合法时机；指定局部帧是可选扩展，需另定时钟与不合法时的处理。这些尚未实现，正式化时遵守总设计 T6–T7、TD-04 与 TD-09 的变更约定，详见 [CD-01](codex-debate.md#cd-01)。

### 3.4 完整状态、时钟与存档的类比

两个状态可能拥有相同的血量、协奏、能量和可见 buff，但其中一个还有攻击正在飞行，下一帧会命中，另一个没有。它们的未来不同，不能视为相同运行状态。

完整状态更接近可继续运行的游戏存档：当前和后台动作、局部进度、资源、冷却、充能、钩子 `vars`、buff 实例、内部触发冷却、未结算判定、尾部、敌人状态、膨胀窗口、调度位置、待处理切入/延奏以及 RNG 等。

世界帧、战斗时钟、动作局部进度沿用 T2、TD-04；录像时间是需要映射的外部坐标。录像为 30 fps、经过剪辑或存在 HUD 刷新延迟时，乘以 60 不会凭空获得逐帧测量精度。

### 3.5 轴的转写也是模型输入

采纳 Claude §1.5：教学原文的 `e`、`z`、`闪` 不是天然唯一的动作 ID。同一个键在不同形态下对应不同动作；把它写成具体动作就是一次解释。建议保存“原材料位置 / 原文记号 → 所选动作 → 采用理由或其他读法”，然后再连接现有 `CommandRef`。例如不能只保留“第 4 行执行 E2”，还应能查到为什么把原文那个 `e` 读成 E2。第一版用显式映射即可，不要求先做自动读轴或复杂语法；有歧义时按 AGENTS.md 另存对照场景，不静默改写原轴。

| R11 | 没有 `res.error` 不代表分析窗口完整；估算状态还会在下游丢失 | 截断场景复现，消费者代码核查 | 将完成范围与目标是否达到传到比较结果 |
| R12 | 文档状态和“已处理 flag”容易被误读为当前验证覆盖 | README、正式文档、构建与模块交叉核查 | 建当前能力索引，区分采用与证实 |
| R13 | 假设名、可调路径与独立游戏命题没有一一对应 | 交叉阅读后核对：40 条中 14 条有 `adjust.path`；17 处 `module-guess` 调用分布在 12 个模块；心与卜灵共用保留状态开关 | 按命题拆 ID 与候选，优先解除已影响判断的耦合 |
| R14 | 命中与其他资源变化采用两种输出表示，下游重复重放 | `settleGains` 写 `hit.gains`，`grant` 写带绝对值的 `resource`；这是现有设计，不单独判作数值 bug | 先提供统一读取视图，改变业务事件种类需另验触发语义 |
| R15 | `fit` 未纳入单下跳字，且不同性质的候选共用榜单 | `replayFit` 不读 `video.hits`；`fitVariants` 合并开关与改轴候选；评分已有显式启发式权重 | 补跳字通道、区分候选类型；分数只作排序，保留缺失和分项证据 |

### R01：量尺不一致，无需新增游戏实测即可定位

[calibration.schema.ts](../src/data/calibration.schema.ts) 的 `kind: loop` 注释及 [校准说明](calibration/README.md) 定义为世界秒；[calibration.ts](../src/engine/calibration.ts) 的 `simValue` 返回 `span.endT - span.t`。根据 [types.ts](../src/engine/types.ts) 的 `EventBase`，`t` 为战斗秒。

本 session 已复现，2026-11-08 整理时再次执行：

```bash
node --import tsx --input-type=module <<'JS'
import { simValue } from './src/engine/calibration.ts';
const log = [
  { type: 'loop', loop: 1, f: 0, t: 0 },
  { type: 'loop', loop: 2, f: 600, t: 6 },
];
console.log(simValue({ kind: 'loop', loop: 1 }, {}, log));

```

当前输出 `[6]`。若观察的是录像经过时间，应比较 10 世界秒；若观察的是停表后的战斗计时，应比较 6 战斗秒。这个 JS 复现仅调用 loop 分支，省略了它不使用的其他输入字段，不能当成完整场景模板。

**更正初稿判断的力度**：TD-11 §1.2 明确说“一轮几秒”通常指战斗秒，`summary.ts` 的分轮也按战斗时钟。现在的问题首先是不同文档和字段契约冲突，不能据此直接把 `endT - t` 改成帧差。应在观测中明确时钟，再规定旧字段的默认含义并检查消费者。

这不是游戏实验。当前 37 个登记点均为面板或跳字，且 `game: null`；不能据此宣称已有某个实测时长被误判。本 session 未改校准实现。

### R02：直接原因应随事件保存

[trace.ts](../src/engine/trace.ts) 的 `walkOwners` 部分依靠最近动作、命中和 buff 到期事件推断归属。注释明确写出：同一帧多个 buff 到时，它们引出的后续事件可能全部归到最后一个到时 buff 的起因上。

可以类比为两笔转账同时发生，账本只保留到账顺序，没有保存各自转账编号。未来应让资源变化、判定生成、buff 施加/到期携带直接原因引用。

这首先影响解释和排查。归属推错不自动意味着结算数值也错。需要新增人造案例分别验证数值与来源，不能仅修改展示后就声称机制被验证。

延迟效果还要把最初来源带入判定、计时器或尾部，不能只依赖当前正在处理的事件。伤害持有者、触发者和数值贡献者也要保留各自含义。

Antigravity 补充的队列交错例子有价值：E1、E2 已入队，处理 E1 时才追加 C1，日志顺序会是 E1、E2、C1，邻近关系不代表父子关系。核对时还要修正实现描述：`bus.current` / `bus.chain` 当前保存的是 `{ depth, root }`，并没有直接父事件的完整字段；处理循环的 `i` 才是当前事件下标。可以利用这个位置补记录，但不能把已有的 root 当成 parent，更不能只沿触发父链就声称找到了全部规则影响。

### R03、R06：贴合分数与诊断证据分别使用

[fit.ts](../src/engine/fit.ts) 的录像动作匹配逐条寻找 10 秒窗口内最近的同名动作，尚无一对一约束。本轮用 `wait 720` 后仅执行一次“甲 X”的人造场景，传入 `video.events: ['10 甲 X', '14 甲 X']`，得到 `n: 2, matched: 2, mae: 2`。两条观测共用了第 12 秒的同一动作，漏一次动作并没有体现为未匹配。

同一场景只给一个不存在的第 99 行锚点（`marks: {99: 50}`），不提供其他观察，得到 `switches.n: 0`、`events.n: 0`、`score: 0`。`compareMarks` 能产生 missing 信息，但 `replayFit` 没将它转成不可评估状态或缺失项。0 分在这里表示没有成功参与比较的数据，不能解释成完美贴合。以上是新做的本地函数复现，未新增仓库测试文件。

已有 `Fit` 保留切人、动作、血条、协奏、核心资源的分项信息，可继续使用。改进重点是先建立合理对应，显示缺失与歧义，再看各通道的差异；总分继续用于候选排序，不能用一项变好抵消关键规则的反证。

采纳 Antigravity 对漏掉 `video.hits` 和混排候选的提醒，但更正“不同量纲直接裸加”的说法：代码的 `FIT_WEIGHTS` 明确把类型错、缺动作、血条和资源偏差折成约定的秒数惩罚。它是人为定义的排序尺度，不是物理误差，也不是概率。建议将“改规则”和“改输入”分组，显示分项变化、有效观测数和定性冲突，再按公开权重选择是否排序。跳字应保留未知暴击分支，不能为了避免自动选近支而默认所有观察都是暴击，详见 [CD-06](codex-debate.md#cd-06)。

[calibration.ts](../src/engine/calibration.ts) 会在非暴击与暴击值中选最接近实测的一支。这可用于寻找相容解释，却不能证明暴击状态已被独立观察。观测没有覆盖的内容，应显示未验证，不能包装成零误差。

### R04、R08：展示轨道不是完整存档

[simulate.ts](../src/engine/simulate.ts) 每次从 `initialState` 开始，输出日志、汇总、回路显示和冷却轨道。回路显示主要是变化时记录的说明文字，不等于所有钩子内部变量；事件日志也不是已验证完整的状态恢复格式。

还要区分“日志中排在前面”与“处理该事件时状态是什么”。例如内核先记录 `actionStart`，其回调再扣能量并调用 `drain`；角色钩子消费 `actionStart` 时已经可以看到扣除后的状态。仅按日志顺序逐条套回去，并不能自然获得每个钩子实际读到的状态。现有回路/冷却轨道又主要在 P6 采集，不能直接当作 P1 前的快照。

第一版 `stateAt` 可从相同输入重算到指定边界，读取执行器状态。返回数据与运行中的可变对象隔离，查询本身不推进时间或触发效果。之后再考虑快照和分支。

运行时恢复还需审计 `Sim` 中事件队列游标、链条记录、警告集合等内容如何保存或重建。不能仅凭 `SimState` 能复制，就认定恢复正确。

[portable.ts](../src/engine/portable.ts) 去掉装配结果中的钩子表，使输入可 JSON 往返；[conformance 命令](../src/cli/conformance.ts) 输出装配输入、事件日志、汇总和报错。它们为移植提供了基础，尚不等于暂停/恢复、查询重算和分支运行已经验证。

### R05：观察过程必须不改变执行

[triggers.ts](../src/engine/triggers.ts) 的 `drain` 消费 `s.log`，角色钩子会收到事件。若把新的调试条目直接加入业务日志，可能增加钩子调用或改变事件链处理。

建议诊断走独立通道，或使用不会产生新业务事件的元数据；不额外消耗业务实例编号或 RNG。验收时比较开关诊断前后的业务事件、状态、数值、报错与抽样结果。

这不要求把整个内核改写成所有赋值都产生事件的系统，也不要求引入动态代理追踪所有字段访问。先在已有资源、buff、判定和动作操作处记录关键事实即可。

### R09：同名 buff 的提供者在输出中丢失

TD-07 §2 规定 buff 身份是 `(defId, owner, target)`，同一武器两人各带是两条实例。[buffs.ts](../src/engine/buffs.ts) 按此区分运行状态，但 `buffApply` / `buffExpire` 日志没有提供者或实例 ID；[summary.ts](../src/engine/summary.ts) 的 `buffUptime` 只用 `buff→target`，网页共用数据中的 `buffOwners` / `buffInfo` 又只用 buff 名作键。

本轮复现：甲在第 0 帧给全队施加持续 60 战斗帧的“共享效果”，乙在第 30 帧施加自己的同名效果，统计窗口为 `[0, 110)`，没有时停。甲的在第 59 帧 P6 到期，乙的在第 89 帧 P6 到期。

| 量 | 应按当前实例规则解释为 | 当前输出 |
|---|---|---|
| 至少有一份效果存在的时间 | `[0, 90)`，覆盖率 `90/110 ≈ 81.82%` | `60/110 ≈ 54.55%`；第一份到期后后半段丢失 |
| 谁提供效果 | 甲、乙，各有实例 | `timelineModel.buffOwners['共享效果']` 只剩乙 |

这是报告与运行模型之间的信息损失，不是用人造场景证明游戏里某两条加成必然叠加。单个提供者的已有场景不因此自动判错。修复时应先保留身份，再决定报“每个提供者的覆盖率”“至少一份存在的覆盖率”或“实际生效覆盖率”；不能仅把两段时长相加，也不能只改网页标签。

### R10：击杀分数与分项伤害没有共用一致的边界

`summary.ts` 的 `goalSummary` 用“目标血量 ÷ 击杀时刻”评分；`analysis.ts` 的 `dpsBreakdown` 则按 `[lo, hi)` 选命中，`hi` 恰好是致死一击所在帧。

本轮人造场景：敌人生命 100，唯一一次命中在第 10 战斗帧，期望伤害 463.25。结果为 `goal.reached: true`、`goal.dps: 600`，但 `dpsBreakdown(...).byChar` 是空表，因为第 10 帧被右端排除了。现有“分项相加等于 DPS”的说明在这个目标下不成立。

只改成包含终点仍不够：463.25 的实际伤害含溢出，而击杀分数的分子是 100；同帧多个命中还要按事件顺序定位真正的致死事件。应明确分项展示的是实际伤害贡献还是扣除溢出的有效扣血。前者不应声称加总等于击杀分数，后者需逐事件裁切致死命中。稳态和固定时间窗继续使用既有左闭右开口径，不宜整体改成闭区间。

### R11：执行未完成、目标未达到，也需要被调用方看见

`runLoop` 达到 `maxFrames` 时，仍有指令则报错；指令已发完则只写 warning 后返回。后者甚至可能还在播放最后一个动作，不只剩尾部。

本轮复现一个 60 帧动作，第 30 帧才命中，轴只有该动作，`maxFrames: 10`。运行结果没有 `error`，但有 `maxFrames` warning，统计窗口变为 10 帧、伤害为 0；提示却写着“0 个判定、0 条尾部没走完”，没有描述仍在进行的动作。`basisOf` 仍把它包装为普通“整个窗口”的数字。

另一个边界是未达击杀目标：`Summary.goal.reached` 和 `goalNotReached` 本来就能区分预测内实际击杀与后续外推，但 `Basis` 不保留该状态。`compareRuns`、CLI 对比与网页对比没有统一传递这些警告；搜索主要检查 `res.error`。因此不能用 `!res.error` 作为所有用途的有效结果判定。

建议最小补充为：停止原因、实际执行范围、统计窗口是否完整、目标是否达到、是否外推；消费者按用途决定能否比较。到上限只截掉统计窗口外的尾部，不一定影响窗口内 DPS，不能把所有 warning 一律视为失败。相反，窗口本身未跑完时应明确不可作完整结果排名。这里保留部分日志的设计有价值，需要完善的是状态传递和使用边界。

### R12：当前能力、采用状态与游戏证据应分别表达

几类漂移会影响新使用者和 agent 对引擎的判断：

- README 仍写 M1“待接入构建产物”、M2“待接伤害、常驻 buff 与场景文件”，实际这些早已接通。
- TD-11 的等待表把切人冷却简写成“两次切人至少隔 60 帧”；调度器实际检查切入目标的 `switchCd`，切出时为离场角色设置冷却。文档需要写清冷却的作用对象，不能据简写另造全局切人间隔。
- `engine-quality-plan.md` 的“游戏对上的点为 0”是 2026-10-22 的历史状态。后续三火录像已留下核对记录；37 个正式点仍未填写不能推出全项目没有游戏证据。
- `applyOverride` 会根据覆盖字段或 `accept` 消掉 flag。这表示采用了某个处理，不能推出已经得到独立实测确认。心的转相锁 255 帧就是写在模块里的推断，模块注释仍明确记录其依据。

本轮曾把“手填切人锁仍保留 `switchLockFromInvincible`”当作疑似错误：人造覆盖 60→20 帧后，关闭无敌锁开关会把切人从第 20 帧变成第 0 帧。但继续阅读心的模块后发现，当前手填值本来就来自无敌时长推断，保留该假设身份有合理用途。因此没有将它列为已确认 bug，也不建议机械删除这个标记。真正需要明确的是：某个覆盖是替换数值，还是连同适用假设一起替换。

后续可维护一张小的当前能力表，给关键规则分别记录当前采用的读法、旁证与列明条件下的实测支持。历史记录保留日期和当时配置；不需要重写全部历史文档，也不以“无 flag”当成准确性证明。两个维度的修订见 §5.3。

### R13–R14：采纳结构问题，避免把修法扩成新的隐含规则

Claude 对假设粒度的提醒成立。[assumptions.ts](../src/engine/assumptions.ts) 的 `forteKeepOnSwitch` 同时控制心的形态与卜灵的卦象，它们的实验答案可以不同。`module-guess` 则把多类推断混成一个 ID，妨碍定位与独立比较。不过 17 个调用点不等于恰好 17 条独立事实：例如莫宁的两处调用表达了同一种“进入观测按起手算”的读法。应按可以分别反驳的命题拆分，而非按调用点数量机械拆分。

14/40 是“有自动比较路径的条目比例”，不能叫模型验证覆盖率。表内还含期望暴击、单目标范围、尚未建模能力、操作策略和粗粒度机制集合。不是每条都适合布尔翻转；没有合理替代实现时，应先记清候选与尚不能比较的原因。优先拆心/卜灵的耦合、给影响大的模块推断独立名字，并保留 T16 的假设入口。

Antigravity 指出的资源双表示也确实存在。[resources.ts](../src/engine/resources.ts) 在共同的 `add` 里修改状态，但 `settleGains` 明确只返回命中增量，其他路径的 `grant` 记录 `resource`。我认可统一读取口径以减少下游重复重放；第一步可以提供只读资源账本，把两种来源投影为同一种变化记录。直接给每个命中再补发 `resource`，会改变 `drain` 消费的事件，不能当作无副作用整理；也不能把该账本称为完整运行状态。迁移与诊断的验收见 [CD-04](codex-debate.md#cd-04)。

## 5. 证据链：来源、执行与现实支持

证据链要回答三个不同的问题：这个数据/规则从哪里来；本次程序为什么这么算；有什么游戏观测支持它。

### 5.1 一个贯通的例子

仍使用虚构的 E：

```text
原始资料：“协奏 +10”
    → 当前采用的解释：“E 首次命中时增加 10”
    → 本次第 4 次 E 的首次命中
    → 协奏由 90 变为 100
    → 下一次调度满足变奏资源条件
```

“10”的数量有出处，不表示“首次命中时”的时机也有出处。资料只写总量时，时机应单独标为推断。发生的每次变化则指向具体动作与命中实例，而非最近的同名动作。

建议优先为高影响疑点记录：原始文件/版本/位置和原文；解析、换单位与覆盖过程；当前采用值或规则；其他候选与采用理由；支持/冲突的观测；适用条件；回归案例。已有 generated 出处、curated、flags 和假设表可作为起点，不需要先给所有字段建一套复杂证据数据库。

来源按具体内容评价。解包字段可能提供数值，但仍需知道调用分支与运行时修正；说明文本可能不包含同帧顺序；录像只覆盖一次可见过程。同一上游被多个网站转载，不能当成多份独立支持，也不宜给整个网站一个统一概率分数后机械传播。

采纳 Claude §5 的具体做法：修正一种读表错误后，查找全库同类写法，适合自动识别的固化为 flag。空白优先级、空白膨胀类型、落地后重新计帧等，应作为转换规则审查，不能只补某个角色的数值。AI 整理、三方 review 和分组对比也都是二次材料；多个 agent 复述同一句话不构成多份独立证据。倍率互证可以降低补测优先级，不足以把相关调用分支与所有场景一起判为已证实。

执行因果与数值依赖分别记录：某次队友命中触发协同攻击，是触发关系；这一下使用哪些攻击、倍率、buff 与敌人条件，是数值依赖。内部因果链解释程序，但不会自动发现尚未实现的游戏机制。

### 5.3 运行身份和适用范围

建议运行记录关联场景/初态、装配数据、数据源标识、实际规则开关、引擎与钩子代码、操作策略、抽样种子、输出版本和完成范围。未提交的机制改动也可能改变结果，只记录 xlsx 版本不够。

保持 T15 只维护当前版本的取舍。记录身份是为了解释变化和检查证据适用性；没有保存对应输入与可执行代码时，一个哈希不能保证未来重跑。重要案例可保留必要材料，不据此扩展成多版本游戏服务。

接受 Claude CL-01 对我原先措辞的修正：**“当前采用什么”与“有什么证据”是两个维度**，不能把 Adopted、Corroborated、Verified 排成一条升级路线。一条实测支持的解释可以暂未采用；一条正在采用的解释也可能有反证。证据应关联具体候选、条件与版本，保留支持和冲突。优先扩展现有 `assumptions.ts` 的身份与索引，原始录像、读数和详细实验记录仍各有出处，不另维护一份相互竞争的手写总表。

已知而尚未接运行时开关的候选也应登记，标 `implemented: false`，不能把“敏感度未测”显示成“没有其他解释”。未知机制也不必硬凑备选，可记录候选尚不完备。`module-guess` 的 17 次调用、16 种不同说明文本不是独立命题的固定数量；应按可分别检验的事实拆分。类型化 ID 与生成文档能检查引用、减少重复维护，不能自动证明语义与证据条件仍一致，见 [CL-01 本轮确认](claude-debate.md#codex-turn-2-cl-01)。

版本变化时，旧观测仍是旧版本的事实，当前适用性则需另评估。数据变化可触发复核，但数据未变不能证明共享规则未变。可以有依据地暂时沿用并标注“旧版证据、当前待复核”；不全量作废，也不静默升格为当前已验证。应区分观测的游戏版本、数据材料标识和运行代码/输入身份：当前 `GameData.version = 20261019` 来自 xlsx 文件日期，不是游戏版本号；清单的 `resourceVersion` 与录像客户端的对应也需有出处。版本未知就保留未知，不直接比较这几类字符串。自动关联变化字段与需复核规则是待实现能力，先从高影响规则的明确引用做起。讨论见 [CD-05](codex-debate.md#cd-05) 与 [CL-05 本轮确认](claude-debate.md#codex-turn-2-cl-05)。

## 6. 怎样管理“当前观测无法确定原因”

目标是尽量设计出可区分的观察，并让每个剩余疑问都有具体候选、影响范围和下一步。不能承诺从缺少区分信息的材料里唯一恢复真实机制。

### 6.1 相同总量可以对应不同机制

假设没有其他回协奏效果、没有溢出：

| 候选 | 起手后、命中前增加 | 命中后累计增加 |
|---|---:|---:|
| A：起手给 10 | 10 | 10 |
| B：命中给 10 | 0 | 10 |
| C：起手给 5，命中给 5 | 5 | 10 |

只看技能结束值，三者无法区分。在这些候选对此观测预测相同的前提下，重复录同一结束值仍无法区分。动态模型校准研究把可辨识性与缺乏有信息量的实验数据列为重要难点；本项目可先用这样的小候选表处理，不直接套用连续动力学的复杂算法。[A protocol for dynamic model calibration](https://arxiv.org/abs/2105.12008)

有价值的下一项观察是命中前的资源。实验要控制初始值、避免上限截断、排除其他回资源效果，并确保画面能分辨候选差别。若 HUD 读数不够精确，可寻找满足其他条件时的离散门槛现象作辅助观察。

### 6.2 实验先写预测，再采集

每次实验先明确：各候选会看到什么、差别是否超过读数误差、什么结果会反驳哪种解释、准备和重置的成本。优先查已有材料是否已包含这种观察，再决定新增实测。

有些候选预测确实不同，却只差 1 帧，而定位误差有 3 帧。这时应改善量法、换差异更明显的条件，或保留范围。重复有助于理解噪声，不自动消除系统性对时偏差。

需要区分数值参数与机制结构。例如“命中加多少”可以扫描有依据的数值范围；“起手给还是命中给”适合离散候选。不要用一个任意的中间时刻或伤害补偿系数掩盖机制分歧。

怀疑交互时，要比较无效果、A、B、A+B 等必要条件。单独观察 A 和 B，不足以证明两者同时存在的规则。按结论需要选择少量组合，不做没有边界的全排列。

### 6.3 让疑问成为可管理对象

建议的一条记录示意：

```text
疑问：E 的协奏何时到账？
当前候选：起手 / 命中 / 分两次。
已有约束：目前仅确认最终累计 +10。
当前采用：命中到账，标为假设。
受影响的问题：命中前是否已满足变奏资源条件。
下一项观察：低初始资源、无额外回资源时，读取命中前的协奏。
仍缺条件：画面是否能区分 0、5、10 的变化。
```

每个选定候选下仍进行确定性仿真。外层分别跑候选，再比较结果；不需要在单次运行中随机猜规则，也不把未经建立概率的候选平均成“真实值”。候选最小/最大值只是已列候选下的范围，不是统计置信区间。

按影响安排后续：

- 当前候选都支持相同结论：可以发布带候选范围的稳定结论。
- 候选改变关键门槛、动作必要性或容错：优先设计区分实验。
- 影响小：按 T16 登记，延后实测。
- 所有候选都无法解释观察：检查量法、输入和遗漏机制，不把最接近者直接定为真。
- 在当前用途和观测范围内无法区分：保留候选，说明什么新增能力或观察才有机会区分。

一次只翻一个开关的敏感度分析，不保证所有未知机制组合下都稳定。结论应注明实际检查的范围。

同理，输出应分开“完整规则配置”“运行中读过或影响过局部判断的规则”“针对某个结果重跑后测得的变化”。直接原因链回答谁触发了谁，不能完整回答哪些历史时序与资源决定了这一下。尚未覆盖的依赖应写成未分析；具体口径及跨运行匹配见 [CD-02](codex-debate.md#cd-02)。

跨运行匹配须先检查执行覆盖：变体提前停止、没有执行到目标段，不能标为目标事件消失；可用“未分析 + 未执行到原因”，并另列完成范围。即使两边都覆盖了该段，结构键无法唯一对应时仍应报告歧义。四类依赖输出不存在自动的上下界包含关系，按需反事实的结论也只覆盖指定的改动与条件，见 [CL-02 本轮确认](claude-debate.md#codex-turn-2-cl-02)。

2026-11-09 续议确认：可以补充单次命中距相符 buff 窗口边界的帧余量，帮助识别值得重跑的临界点。它需保留实例、持有者/目标、过滤条件、退出原因和同帧相位；完成运行中的前后事件与当前快照能知道的内容分开。接近到期不等于挪动命中就必然保住该 buff，见 [D-AG-04 收敛记录](antigravity-debate.md#codex-turn-2-d-ag-04)。

### 6.4 独立检验与停止条件

用于调整模型的片段，与保留作检查的片段分开；优先按不同实验、录制或条件划分。同一段录像中相邻的许多帧，不等于许多份独立证据。

问题可以收敛为：实现错误已修复；某机制在列明条件内得到支持；参数范围缩小；现有观测无法区分；超出当前模型范围。后两者也应交付明确记录和影响，不强行把残差调到零。

## 7. 差异收敛的工作流程

建议将 TD-11 已有“说清楚、分层、从粗到细、做实验”的方法进一步落成统一输入输出。

| 步骤 | 具体工作 | 产物或边界 |
|---|---|---|
| 1. 确认可比 | 时钟、单位、配装、版本、敌人、环境、初态、模型范围 | 可比较，或明确缺少的条件 |
| 2. 匹配对象 | 按角色、形态、动作、实例、顺序和锚点对应；一般一对一、顺序一致 | 匹配、缺失、歧义；聚合观测明确范围 |
| 3. 分开残差 | 事件数量/类型、时间、资源、buff、单次伤害、累计血条 | 不让总分隐藏互相抵消的错误 |
| 4. 找到最早有证据的偏差 | 两份完整模拟可精确比较；稀疏录像只能限定最早可见偏差 | 不推断更早隐藏状态已经正确 |
| 5. 沿依赖缩小 | 找字段上次变化、直接原因、数据与规则；保留必要铺垫形成小案例 | 不随意删除初态或改掉原问题 |
| 6. 列候选 | 区分读表/单位、程序、参数、机制、转写、缺失能力 | 少量有理由且能产生预测的解释 |
| 7. 选择区分观察 | 检查已有证据，再比较新实验的信息量与成本 | 预测表、实验条件、允许误差 |
| 8. 固化结果 | 记录观测、采用/排除理由、适用范围、实现回归和独立检查 | 可复用案例；未解决项保留下一步 |

比较游戏观测还要考虑测量过程：资源环是近似读数；单次跳字有暴击分支；累计血条会受到实际暴击序列影响。默认期望伤害不应被要求逐次等于录像伤害，搜索一个最贴合的随机种子也不能验证机制。

强制指定的能量、失谐和动作时刻属于输入条件。用它们复现后续过程有价值，但不能再用同一个被指定的量证明模型自主预测正确。

吸收 Antigravity 的局部诊断思路：记录同步前预测、观测约束和实际注入，可以阻止前段差异拖垮整局分析。但“看到变奏”主要约束入场条件，不能恢复全部隐藏状态；注入量也可能来自漏读动作、初态错误或模型缺口。录像时段至少区分已观测动作、已确认无额外输入、未知输入。现有 `at` 已会等待，不需要靠补位才能让时间走过；空等也会推进后台判定、buff 与时钟。未知区间用哪个候选继续必须显式说明，见 [CD-03](codex-debate.md#cd-03)。

2026-11-09 续议明确采用的规划默认：状态补全的 `sync` **不发业务触发**，因为“此刻采用满资源”不能证明“资源此刻刚刚攒满”。观测约束、采用值、注入量、相位与未派发事件走旁路记录；显式要求业务触发时，另记其假设。具体受影响效果仅在可诊断范围内列出，未知钩子不冒充已分析。环境输入与补状态分开，从首次注入起保守标记后续条件推演。此契约尚未实现；确认理由见 [D-AG-02 收敛记录](antigravity-debate.md#codex-turn-2-d-ag-02)。

对录像空当采用“已观测动作 / 有依据的空闲 / 未观测区间”，不新增“距离 `at` 太近就禁止补位起手”的调度启发式。没有跳字不足以证明空闲；未观测区间可试填候选，但结果不是包住真实状态的上下界。以后若明确设计新的取消策略，仍可调整调度器，现有快照本身不是禁止改变的理由，见 [CL-03 本轮确认](claude-debate.md#codex-turn-3-cl-03)。

### 7.1 读已有结果与设计新实验采用不同的检查路径

我认可 Antigravity 的静态面板、buff 比值、单段资源、局部动作间隔这组隔离手段，也接受两位新版提出的区分：已有录像先确认可比与对应关系，再沿最早可见差异回查；新实验则主动控制无关变量。它们是互补工具，不要求每个资源问题都先重测伤害公式，也不意味着“某层对过一次就永久排除”。

比值可以帮助提出更少、更清楚的候选。例如心队早期两类跳字的比值可试写为 `共同乘数 × (1 + 额外增伤 / 原增伤底数)`，用前段估计、向后段作预测。但共同乘数未必就是攻击力，两个数能拟合不等于找到了两条真实 buff；局部时间归零也只去掉时间偏移，不会清除入场前继承的资源与 buff。心队案例的重新计算、替代解释与区分实验见 [CD-07](codex-debate.md#cd-07)。

**续议更正：旧表的仿真列不是当前运行。** Antigravity 指出、Claude 随后核对镇寰宇的数值漂移；我也独立重跑 `bebd9f8` / 装配数据 `20261019` 的 `xin-tower4-video.yaml`，确认当前镇寰宇暴击为 **180256、增伤底数 3.016**，不是旧表的 195198 / 3.266。此前的后段拟合仅对旧表成立，不能用作当前模型的吻合证据。在内存中只对调雷主首位为绝息魄，前段 QTE/镇红尘的录像与仿真比值分别变为 1.0436654 / 1.0436974，照世 E 为 0.9995761，支持优先核对实际首位；当前镇寰宇边界差异仍未解决。录像首位、真实 buff 状态和游戏战斗时间尚未新核验；不能以模型输出的两战斗帧间隔直接推断游戏也如此，或排除未明确触发点与时长的全部世界时钟候选。复现数据、推理边界及剩余收敛条件见 [D-AG-03 第 2 轮回应](antigravity-debate.md#codex-turn-2-d-ag-03)。

## 8. 应用怎样验证底座

应用提供真实组合场景，底座积累可独立运行的机制案例。它们之间可以形成长期复用关系。

| 验证材料 | 主要支持什么 | 仍不能单独推出什么 |
|---|---|---|
| 人造小场景、手算边界 | 程序按所声明顺序与规则执行 | 游戏也采用同一规则 |
| 数据构建和公式对拍 | 转换、公式与参照一致 | 上游参照完全正确 |
| 受控短实验 | 特定条件下的时机、资源和数值 | 所有角色和上下文通用 |
| 完整实战或教学场景 | 多机制组合、实际输入、旧问题是否重现 | 一局总伤害贴合验证了全部机制 |
| 另一实现与 conformance | 实现遵守共同执行契约 | 两边未继承同一错误模型 |

优先复用现有资料：37 个正式校准点尚无实测值，不代表项目没有实测证据。角色测试和录像复盘已保存部分数字与修复过程，应先整理关联，避免从零重测。

对教学轴，“必要性”要附条件：在这个起点、保留这些后续操作和目标时，某动作不能直接删除；它不证明所有打法都必须用这个动作。容错则应显示在所测延迟范围内，首次损失的是哪项资源、命中、buff 或后续窗口。不能仅从 DPS 是否变化解释操作用途。

深塔、矩阵、全息应用继续说明所需的敌人阶段、场地、目标数量和命中条件。当前单目标等边界沿用总设计；未建模能力不能用伤害倍率补偿后当作已支持。

### 9.1 建议接口，不是现有命令清单

|---|---|

### 9.2 P0–P4 的增量路线

以下编号属于本轮底座提案，不等同于 `engine-quality-plan.md` 原有 P1–P6。它们是后续实施建议；用户本轮要求先讨论和记录。**2026-11-09 修订：这些是能力批次，不是必须全部串行完成的时间表；P3 的证据工作从第一批就开始。**

| 批次 | 最小工作 | 验收方式 |
|---|---|---|
| P0：量尺与结果状态明确 | 统一校准时钟/单位，补实例身份、目标统计边界、完成范围和缺失观测状态（R01、R03、R09–R11） | 10 世界秒 / 6 战斗秒分别正确；两份同名 buff 不丢；致死命中可解释；无有效观测不报完美匹配；窗口未完成不冒充完整结果 |
| P1：执行可查 | 关键事件直接原因、独立诊断、重算查询状态 | 同帧两个到期效果不串来源；查询和开关诊断不改变结果 |
| P2：差异可定位 | 实例匹配、分项残差、最早可见偏差、依赖回溯 | 能区分单位错误、漏动作、资源时机；资料不足时保留候选 |
| P3：规则有证据（贯穿各批） | 首批字段/规则来源、候选表、旧证据整理、独立检验与回归 | 已解决案例能追到依据；未解决案例能明确缺哪项观察 |
| P4：调用与效率 | 统一机器可读接口，按实际需要增加快照/恢复 | 从头执行、查询重算、恢复续跑一致；agent 无需猜单位或解析网页 |

本轮对优先级的调整是：**先保证现有工具不会因丢身份、混边界或遗漏完成状态而给出误导结论，再扩展完整状态查询。** 这些问题能用软件小案例推进，不能一概转化为“还要进游戏测”。不必等它们全部解决才设计查询接口，但不应把错误的现有汇总直接当作新接口的可信参照。

接受 Claude §8 与 Antigravity D-AG-01 的修正：**修软件量尺与准备短实验可以并行**。B1/B2 的切走保留观察，不需要等击杀分项统计修完；反过来，R09/R10 的软件复现也不需要等用户进游戏。具体实验只依赖它实际使用的读数与预测工具。第一包可从 [verify-guide.md](verify-guide.md) 中 B1、B2、A1、C1、B11 按同账号和重置条件安排，B10 作为独立的交互实验；时间是手册估计，另计换号、准备、失败重录与读数整理，不能承诺一次全部定案。这里 A1 是**心的面板与开场 AAA**，C1 是**椿烬华蔓舞后是否自动出第四段**。

实施可按案例交叉推进，不必先给所有状态、所有字段做完完整平台。首批建议为：

1. 世界秒与战斗秒：纯软件小案例，先验证比较工具。
2. 两个提供者的同名 buff、同帧两个 buff 到期：分别验证身份保留和直接来源。
3. 单击击杀、动作未结束即达帧数上限、录像锚点全部失配：验证结果的使用边界。
4. 散华 E 和焰痕延长：复用既有数据与游戏记录，走通来源、执行、解释、回归的连接。
5. 卜灵协奏时机：保留未解问题，交付候选与区分实验，检验系统能否管理不确定性。

底座第一阶段完成的含义是：支持范围内的状态可查、关键事件可解释、比较方法经过检查、至少有真实案例走完诊断过程，同时能正确处理一个无法区分的案例。它不代表全游戏数据已校准。

进一步采纳“软件能力与机制可信度分别验收”的提议，但机制基线必须先列明用途、规则集合及条件。某个大影响问题仍分不清，可以完成其诊断记录，却不能因此把依赖它的精确容错结论也标为已验证。角色内容不全量纳入验收，代表性钩子集成必须纳入。候选范围内稳定的结论可有条件交付；范围内会翻转的结论保留限制。首包几个实验不足以声称所有大、中影响共享规则都已定案，见 [CD-08](codex-debate.md#cd-08)。

### 13.2 对底座规划的实质修正

**首先要打通的是“数据 → 执行 → 报告 → 结论”的可靠性。** 本轮 R09 就是执行模型保留了两份 buff，解释层却丢掉了一份；R10 是击杀评分和分项解释各自有算法，却没有共同的边界契约。增加更多实测无法直接修好这两类问题，增加一个查询 API 也不会自动修好。

状态查询应沿已有执行器逐步暴露。建议从一份小的结构化查询契约开始：前台与动作进度、资源、可用冷却、带实例身份的 buff、列明的角色状态、待结算效果及查询边界。对查询范围之外的内部细节明确标注；之后再扩展暂停恢复。不要先承诺每个业务日志事件都能无损重建完整状态。

矩阵是另一类边界：[matrix.ts](../src/engine/matrix.ts) 已明确采用分别模拟每只 boss 再按伤害流接力的近似，敌人的偏谐、异常效应等不是在每次交接时连续演化。这适合已有的粗略比较用途，不能直接验证“新 boss 出现那一帧的真实状态”。以后若要回答该问题，应先明确环境事件与敌人状态连续性的契约；不必为了这次 review 改写矩阵实现。

搜索与择优同样需要明确能证明什么：择优已用完整仿真确认候选结果，能检查快速估值的偏差；但有限候选的完整仿真仍只证明在所测候选和所选模型下的排名。敏感度矩阵是逐项翻开关；“所试单项都稳定”不等于所有机制组合都稳定。现有稳态 `spread` 是窗口改变带来的离散变化范围，也不是统计置信区间，更不包括未知机制误差。

因此保留“底座优先”，但把第一批交付从抽象 API 清单进一步收敛为：**现有结果不会把失配、截断、外推或丢失实例伪装成完整确定的解释；已知真实案例能走通一条可追查的路径。** 做到这些后，教学轴和 AI agent 才能可靠复用同一份底层结果。
