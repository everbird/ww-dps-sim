## 2. 这一轮的教训

1. **优化器会放大模型的错误。** 搜索和排轴专找模型里最划算的地方，模型和游戏不一致的地方往往正是最划算的地方。这一轮碰到三次：
   - 稳态的相位偏差，C2 从 +19.77% 更正为 +9.28%（TD-10 §2）；
   - 卡帧点"晚 6 帧反而 +1.84%"是相位假象；
   - 搜索第一名（卜灵第一段 Q 先放）落在空中入场没问清的地方。

   以后搜出来的大收益，先当成"可能是 bug"查，再当成发现。
2. **量法本身也要验证。** 相位问题不是机制写错，是"稳态怎么取"错了。
3. **功能长得比验证快。** 排查工具（`pnpm trace --hits`、视频时间点、假设表、conformance）都齐了，但还没喂进过游戏里的数字。

## 3. 做什么（按性价比排）

### P1 不变量检查，拿生成的轴当模糊测试（我做，不用等）

- 引擎加一个检查开关，每跑完一次核对：
  - 能量、协奏、核心资源的总量等于各来源之和；
  - buff 覆盖率 ≤ 100%；
  - 总伤害等于逐下伤害之和；
  - 时间单调；
  - 每个动作的判定要么都生成，要么有明确的打断原因；
  - 冷却没被提前用掉。
- 语料：现有全部场景，加上 search / plan / `--gen` 会试的几千条轴。违反的就是 bug。
- 变形关系：
  - 加攻击力，伤害不降；
  - 插入纯等待，DPS 不升，除非能指出哪个机制让它变好；
  - 结果相同的两种写法，结果必须一样。

  卡帧点的"反而更好"就是这类异常，每一条都要解释得了。

### P2 假设敏感度矩阵与结论的依赖（我做）

- 给"未知"的假设补开关（预输入、切人锁按无敌帧还是按动作结束…），已有开关的直接用。
- 每个场景和对照场景，在每条假设翻转后各跑一遍，出一张表："这个结论在哪条假设下会翻、翻多少"。
- `pnpm compare`、search、plan 报收益时，顺带列出"差异部分碰到了哪些假设"（两次运行碰到的假设相减）。
- 用这张表给 `verify-guide.md` 的验证项排先后：翻得越多的越先测。

### P3 量法硬化（我做）

- 稳态窗口自动对齐所有周期过程（谐度破坏几轮一循环、电磁 5 秒结算、各冷却），不再只在出错时提示。
- 汇总给出"窗口挪一下 DPS 变多少"，当误差条。比它小的差异不报"更好"。

### P4 校准跑通，对上的写成测试（要你进游戏；我出表、记录、写测试）

- 先做两份跳字（面板 + 单下伤害）。对上了，公式、倍率、敌人防御抗性这几层就钉住了（TD-11 §2）。
- 再拿 60fps 录像对一整轮的时间与切人点，顺带量手速（假设 `hand-speed`）。
- 机制的是非题（共鸣回路切人保不保留、F1、空中入场…）一题一题关。
- 每对上一项，写成带容差的用例 `tests/calibration.test.ts`。以后改引擎、换数据版本，对上过的点不会悄悄跑偏。现在的快照测试只保证"和上次一样"，不保证"和游戏一样"。

### P5 数据层（等另一个任务的声骸冷却与 nanoka 核对提交后）

- 把"和 nanoka 比冷却"扩到倍率、回能、协奏值，两边同错的才查得出来。
- 集中清心的 30 个 flag：心队所有结论的地基。

### P6 重的，前面做完再说

- 录像自动识别跳字，整轮批量对伤害。
- 拿社区的伤害计算表做单下伤害的交叉核对。
- 换数据版本时自动重跑全部结论、列出变化（结论快照）。

## 5. 结果（2026-10-22）

### P1 不变量检查与模糊测试

- `checkLog`（`src/engine/invariants.ts`）：每次 tick 原有的检查只看"状态在范围内"，这里另查整份日志自洽：
  - 资源：每条 resource 事件、每次结算的 gains 接得上，中间没有没记日志的改动；
  - 动作实例：一开一关；
  - 冷却：没好不出招；
  - 切人：from 就是前台；
  - 日志不倒序；
  - 期望伤害在不暴击、暴击之间；
  - 汇总：总伤害 = 各角色 = 各动作 = 各轮之和，稳态 = 所含各轮之和，覆盖率在 [0, 1]。

  场景快照测试顺带查。
- `pnpm fuzz`（`src/engine/fuzz.ts`）：
  - 每个场景用轴搜索的改法（挪动、去掉、对调任一动作）生成变体，每条跑完都查 `checkLog`；
  - 原轴另查两条变形关系：同样输入跑两次日志一样；生命、攻击、防御各加一点，时间轴不变、每一下伤害不降。
- **结果**：15 个场景、约 2,100 条变体轴（跑通约 770 条）、544 秒，**0 个问题**。M0 的变体多数跑不通（连段中断），覆盖还可以加。
- **卡帧点的"晚了反而更好"**：查了 4 个主要场景，只有 C8 有两处（切心变奏、心增幅强化重击晚 6 帧，一轮反而短 21 帧，+1.11%）。
  - 已解释，不是 bug：自动谐度破坏（假设 `tune-break-auto`）换了时机。原来卜灵大招后再打，多 90 帧；晚了之后失谐落在雷主大招的切人锁里，雷主在本来就要干等的时间里打完了。
  - 引出一个实测项：雷主大招放出后切人锁之内能不能按谐度破坏（verify-guide B9）。能的话这是一处 +1.7% 的打法。

### P2 假设敏感度矩阵

- 补了三个开关（场景 `options.rules`，缺省都是现在的做法）：
  - `forteKeepOnSwitch`：false 时心切走回到应世相、退出心相心生，卜灵切走清卦象；
  - `ultInputLocksSwitch`：false 时大招的"不响应输入"不挡切人；
  - `invincibleLocksSwitch`：false 时没写帧数、推断出来的切人锁不锁（`ActionDef.switchLockFromInvincible`）。

  钩子的 ctx 多了只读的 `rules`。
- `pnpm sensitivity [--md 文件]`（`src/engine/sensitivity.ts`）：内容如下
  - 全部场景 × 假设表里每个开关各跑一遍；
  - 对照场景（文件名 = 基准 + "-差异"）比基准的收益，在哪条假设下会变。
  - 结果存在 `docs/assumption-sensitivity.md`。
- **结论**：让对照结论变了的个数，按开关排：
  - 每个决策点晚 6 帧：7 个；
  - 推断出来的切人锁：6 个；
  - 切人不保留共鸣回路：5 个，C4–C8 全跑不通；
  - 大招"不响应输入"挡切人：3 个；
  - 自动谐度破坏：2 个。
  - 推断出来的切人锁（`switch-no-lock`）原来登记为"影响未知"，现在知道是"大"：verify-guide 的先后已按此调整（B7 提到第 3）。
- **没做开关的**，以及原因：
  - `entry-skill`、`air-entry`：是"这样写轴不合法"的检查，翻过来不改变跑得通的轴的数，只会放行更多写法；
  - `no-input-buffer`：要先有预输入的数据；
  - `wait-settled`：轴里已经能用 `!` 逐个改。
